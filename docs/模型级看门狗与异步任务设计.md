## 1. 背景与目标

DeepSeek 2026-10-31 发布的 Super-agent 架构（Router + Worker、事件驱动、Inline & Spill、异步 ReAct Loop、存算分离 + Watchdog）与本项目对照后，结论是：大部分理念 MeetingRoom 已经用更窄的场景落地（双层调度、事件总线、三层上下文、前缀字节稳定、状态落盘重放）。真正值得引入的只有两件事：

1. **模型级 Watchdog**：现在防"空转 / 偏航"只有程序规则（`maxStepsPerTurn`），`TurnOutcome.HitStepLimit` 可观测但没暴露、更不会干预。缺少一个"用模型判断工作是否取得实质进展、方向是否偏航"的外部控制回路。
2. **异步任务骨架**：现在长耗时能力（图片生成）只在 Host 侧、由用户手动触发，与角色工具面完全隔离。将来若把长耗时能力接进工具面，`StepLoop` 里同步 `await` 会占住整个 step、阻塞该参与者的 turn。需要一个"受理即返回、后台执行、结果作为事件回来"的通用骨架，且**不改 `StepLoop`**。

两项共享同一个总原则：**它们都是"会话主循环之外的低频控制回路"，绝不能挤占与会者的上下文、不能破坏前缀字节稳定、失败不能打断主流程。**

## 2. 现状盘点（接缝在哪里）

| 能力 | 现状 | 位置 |

## 3. 共享设计原则（两项都遵守）

1. **不进主上下文**：watchdog 的输入输出、异步任务的执行过程，都不进任何与会者的 system prompt / 共享节 / 私有历史。与会者能看到的只有"结果投递"那一小段（且走已有注入通道）。
2. **前缀字节稳定不破**：不新增/修改任何与会者的工具集、system prompt、共享节结构；`PromptPrefixVersion` 不因这两项而变。
3. **安静优先**：正常运行时只落盘、不打扰；只有判定"有价值"才发 DM 提醒或注入。对应交互模式已有的 `allowSelfSkip` 哲学。
4. **失败不打断主流程**：watchdog 调用失败、异步任务失败，都只发事件 + 落盘，绝不抛到会话主循环。
5. **"受理/落地"显式化**：凡是"对外返回成功"的路径，落盘必须在返回/发事件**之前**完成（继承 B5 与"对外返回成功 ≠ 内部状态已落地"的教训）。
6. **两种模式共用机制、各自接缝**：机制进 `SessionCore` 或 `MeetingRoom.Agent`；模式差异留在 `MeetingSession` / `RoleplaySession` 外壳。

## 4. Part A：模型级 Watchdog

### 4.1 问题与范围

- **要解决**：弱模型空转（同一工具反复调、产出为空、跑到 `HitStepLimit`）、方向偏航（说书人/主持人的推进与任务无关），现在只能靠 `maxStepsPerTurn` 硬兜，且兜住之后无人知晓。
- **不解决**：程序性故障（接口报错、状态恢复失败）——那些已有 try/catch + 事件；也不做硬终止（`MaxRounds` / `maxSteps` 仍是最上层兜底）。
- **本质**：给会话加一个"低频、独立上下文、用模型判断"的监督回路，对应 Super-agent 的 Watchdog Session。

### 4.2 总体形状

```
MeetingSession / RoleplaySession（会话外壳，各自挂一个后台任务）
        │  每 N 轮 / 每 M 个 timeline 步，或 HitStepLimit/重复工具触发
        ▼
TurnLedger（环形缓冲，内存 + 落盘 watchdog.jsonl）
        │  取最近 K 条元数据
        ▼
WatchdogProbe（MeetingRoom.Agent，独立轻量调用，不走 AgentSession/StepLoop）
        │  一次小请求，要求输出严格 JSON
        ▼
{ verdict: ok | suspect_loop | suspect_drift, reason, suggestion }
        │
        ▼
动作分级：ok → 只落盘；suspect_loop → 软注入纠偏；suspect_drift → 仅 DM 提醒
```

关键决策：

- **A1（独立轻量调用）**：watchdog 不走 `AgentSession` / `StepLoop`。理由：watchdog 不需要工具、不需要 steer、不需要流式正文；把它放进 `StepLoop` 等于让"检测空转的回路"自己暴露在同样的空转风险里。实现上是一个新类 `WatchdogProbe`（在 `MeetingRoom.Agent`，只依赖 `IChatClient`），单次 `GetResponseAsync` + 严格 JSON 解析。
- **A2（输入只给元数据）**：输入是 `TurnLedger` 的元数据窗口（谁、第几轮、工具序列、step 数、产出长度、墙钟、HitStepLimit、SteerCount、缓存命中/未命中），**不含正文全文**。第一版不做"带正文的二次确认"。
- **A3（输出严格 JSON）**：要求模型只输出 `{"verdict": "ok|suspect_loop|suspect_drift", "reason": "…", "suggestion": "…"}`。解析失败 = 按 `ok` 处理（不打扰），发 `watchdog.error` 留痕。

### 4.3 TurnLedger：元数据窗口

新类型 `TurnLedger`（建议放 `Core/Orchestration/` 或 `Core/` 共享），两种模式共用：

```csharp
public sealed record TurnMeta(
    string ParticipantId,
    string Role,            // host | narrator | member
    int Round,              // 会议用；叙事用 timeline.Revision 映射
    string Task,            // 本轮任务指令（截前 80 字）
    string TextDigest,      // 产出正文前 80 字；无产出 = ""
    IReadOnlyList<string> Tools,
    int Steps,
    bool HitStepLimit,
    int SteerCount,
    long CacheHitTokens,
    long CacheMissTokens,
    long WallMs);
```

- 环形缓冲容量 `lookbackTurns`（默认 12）+ 少量超额（便于判定"连续重复"）。
- 落盘：`<会话目录>/watchdog.jsonl`，每条一行 JSON（与 `backstage.jsonl` 同风格）。重启后**只回放进内存缓冲，不重放判定**（判定是实时的）。
- 记录点：会议在 `RunParticipantAsync` 与 `RunHostAsync` 拿到 `outcome` 之后；叙事在 `RunActorTurnAsync` 拿到 `outcome` 之后。**只有开了 watchdog 才记录**（`enabled=false` 零开销）。

### 4.4 触发时机

两级触发，触发后进入冷却（`cooldownTurns`，默认 2 个周期内不再触发）：

1. **事件触发（立即）**：
   - 最近一次 `TurnOutcome.HitStepLimit == true`；
   - 最近 `triggerOnRepeatedTool`（默认 3）条元数据里，同一参与者的工具序列完全相同且非空。
2. **周期触发（低频）**：
   - 会议：每 `periodRounds`（默认 3）轮，在 `RunRoundAsync` 主持人评估之后、`EnforceRoundInteractionAsync` 之前；
   - 叙事：时间线每增长 `periodTimelineSteps`（默认 6）个 revision，在 `RunNarratorReviewAsync` 之后。

实现位置：两个会话外壳各维护一个 `WatchdogPump`（后台任务，注册进 `ExtraBackgroundTasks` 或自管，模式与会议 `_interruptPump` 一致）。它内部订阅判定触发条件，调用 `WatchdogProbe`。

### 4.5 输入装配（prompt 形状）

一次 watchdog 请求的输入（全部由程序拼装，模型只能看到这些）：

```
你是会话健康度检查器。下面是最近 N 条 turn 元数据（JSON 数组）：
[ {participantId, role, round, task, textDigest, tools, steps, hitStepLimit, steerCount, wallMs}, … ]

当前模式：会议 / 叙事
（会议）议题：…；当前第 R 轮
（叙事）世界状态摘要：…；时间线 revision：…

判断：工作是否在取得实质进展、方向是否偏离任务。
只输出 JSON，不要输出任何其他内容：
{"verdict":"ok|suspect_loop|suspect_drift","reason":"不超过 60 字","suggestion":"不超过 80 字"}
```

- `suspect_loop` 判据（写进 prompt 作为引导，最终由模型判断）：连续相同工具序列、产出长度连续为 0 或接近 0、`HitStepLimit`、同一参与者连续多轮 step 数顶满。
- `suspect_drift` 判据：产出/工具与 `task` 语义无关、反复回到已解决的话题。
- 温度建议 0（判定任务不需要多样性）；`maxTokens` 给 256 足够。

### 4.6 判定输出

```json
{ "verdict": "ok", "reason": "…", "suggestion": "…" }
```

`verdict` 只允许三个值；`reason`/`suggestion` 截断到 60/80 字。解析失败 → `watchdog.error` + 本次按 `ok`。

### 4.7 动作分级（安静优先）

| verdict | 动作 | 通道 | 说明 |
| --- | --- | --- | --- |
| `ok` | 无 | 只落盘 + `watchdog.checked` | 不打扰任何人 |
| `suspect_loop` | 软注入纠偏 | 会议：定向 steer（见 4.8）；叙事：时间线追加一条 `note`（见 4.8） | 注入文本用 `suggestion` 包装成明确指令（如"你已连续 N 次调用同一工具且没有产出，请改用……或直接给出结论"） |
| `suspect_drift` | 仅 DM 提醒 | `RegisterSideDecision(PendingDecisionKind.DmNote, …)` 第五列待决卡片 | **不自动干预**——偏航判定不可靠，自动注入可能把剧情带更偏；导演拍板 |

- 硬终止：**不做**。`MaxRounds` / `maxStepsPerTurn` 仍是唯一硬兜底；watchdog 只建议。
- 同一参与者在冷却期内不再注入（防止"注入 → 还是空转 → 再注入"的注入风暴）。

### 4.8 与两种模式的接缝

**会议模式**：

- 现有 `ApplySteerAsync` 是**全员注入**。watchdog 纠偏需要**定向注入**：新增 `SteerParticipantAsync(participantId, SteerNotice)`（逻辑与 `ApplySteerAsync` 单参与者分支相同：运行中 `TrySteer`，成功则记 `_steeredSinceLastTurn` 并广播 `interrupt.applied`；不在运行则记 `_pendingWatchdogSteer[participantId]`，下一次 `RunParticipantAsync` 发起时并进 task 文本）。
- 触发点：`RunRoundAsync` 主持人评估之后。

**叙事模式**：

- 叙事没有 InterruptPolicy，注入 = 追加时间线。新增时间线行类型 `note`（`StoryTimeline` 增加 `AppendNote(author, text)` 或在 `Append` 上扩展），`recall_story` 的 `Kinds` 白名单加 `note`。说书人/角色下一次 `CreateComposer` 的 L2 重建自然看到。
- 触发点：`RunNarratorReviewAsync` 之后。

### 4.9 配置

`meetingroom.json` 新增顶层段（`MeetingRoomOptions` 加 `WatchdogOptions Watchdog`）：

```json
"watchdog": {
  "enabled": true,
  "periodRounds": 3,
  "periodTimelineSteps": 6,
  "triggerOnHitStepLimit": true,
  "triggerOnRepeatedTool": 3,
  "lookbackTurns": 12,
  "cooldownTurns": 2,
  "model": ""
}
```

- `model` 空 = 用 `provider.model`；非空 = 独立指定（可用更便宜的模型）。**校验**：`enabled` 之外，`periodRounds/periodTimelineSteps/lookbackTurns/cooldownTurns` 必须 ≥ 1，`triggerOnRepeatedTool` 必须 ≥ 2；非法值拒绝启动（项目硬约束）。
- 默认全开？**默认 `enabled=true`**（它是低频只读回路，用户价值高），但 `period*` 给的默认频率保守。

### 4.10 事件契约

| 事件 | 载荷 | 说明 |
| --- | --- | --- |
| `watchdog.checked` | `{ mode, round, revision, verdict, reason, tookMs, cacheHitTokens, cacheMissTokens }` | 每次判定后 |
| `watchdog.action` | `{ verdict, action: "none"\|"steer"\|"dm_note", targetParticipantId, text }` | 有动作时（`none` 不发） |
| `watchdog.error` | `{ message }` | 调用失败 / JSON 解析失败 |

- 不进 `meeting.state` / `roleplay.state` 快照（第一版不做前端观察页；导演要看得见就靠 `watchdog.jsonl` 与 `watchdog.action` 事件，DM 提醒已走第五列）。
- SSE 前端**不需要**为这三类事件加 store 归约——`EventBus` 事件只被诊断/观察页消费，前端主 store 忽略未知事件即可。

### 4.11 失败与降级

- `WatchdogProbe` 调用异常 / 超时（`watchdogTimeoutSeconds`，建议写死 30s）/ JSON 解析失败 → `watchdog.error` + 落盘，**主循环不受影响**。
- provider 不可用时 watchdog 静默跳过（与"没有 provider 也能看界面"一致）。
- 会话结束/释放：`WatchdogPump` 随 `ExtraBackgroundTasks` 一并等到退出。

### 4.12 验收标准（probe + 真机，不依赖 `dotnet test`）

1. [空转触发] 用一次性测试数据构造"某参与者连续 3 次只调同一工具且无产出"的会话 → 在预期轮次收到 `watchdog.checked(verdict=suspect_loop)` 与 `watchdog.action(action=steer)`；该参与者下一 turn 的 `SteerCount > 0`（会议）或时间线多一条 `note`（叙事）。
2. [HitStepLimit 触发] 临时把 `limits.maxStepsPerTurn` 设为 1 跑一轮 → 不等周期，立即触发一次判定。
3. [ok 不打扰] 正常会议/叙事各跑 ≥ 2 个周期 → 只有 `watchdog.checked` 落盘，无 `watchdog.action`。
4. [前缀指纹不变] 开关 watchdog 前后，说书人/参与者/主持人的前缀指纹（`PromptPrefixVersion` + tools hash + shared section）逐字节一致。
5. [零开销关闭] `watchdog.enabled=false` → 无任何 watchdog 调用、事件、`watchdog.jsonl` 写入。
6. [降级] 用探针 mock 一个返回非 JSON 的 provider → 发 `watchdog.error`，会话继续推进。
7. [不硬终止] 空转场景下 watchdog 连续触发 → 会话不被结束，仍由 `MaxRounds` / `maxSteps` 兜底。

## 5. Part B：异步任务骨架

### 5.1 问题与范围

- **要解决**：长耗时能力（如"模型生成规则摘要增强版""地图区域描述预生成"）如果作为普通工具接进 `StepLoop`，同步 `await` 会占住一个 step、阻塞该参与者的整个 turn，还会把取消点 B 之前的等待拉长。需要一个"受理即返回、后台执行、结果作为事件回到会话"的通用骨架，对应 Super-agent 的异步 ReAct Loop（`start()` / `stop()`，后台结果作为新事件）。
- **不解决**：不改 `StepLoop`（它是手写循环，动它风险高）；不迁移现有图片模块（见 5.2）；不做分布式/跨进程任务（单进程内）。

### 5.2 ImageStudio 已验证的形状（作为样板）

`ImageStudio.Start` 已经跑通了这条路：**受理立刻返回 `jobId` → `Task.Run` 后台跑 → `image.job(running)` / `image.generated` / `image.failed` 事件 → `_runningJobs` 登记运行中集合**。Part B 把它抽象成工具面可用的通用骨架，**现有图片模块一行不改**；将来若值得，图片可自愿迁入（不在本设计范围）。

### 5.3 生命周期状态机

```
受理(accepted) → running → completed
                        ↘ failed（含 timeout）
                        ↘ cancelled（会话结束/释放）
```

- 受理不是状态：受理动作本身 = 先落盘 `running` 记录、再返回受理凭证（见 5.5）。
- `failed` 与 `cancelled` 是终态；`running` 遇到进程崩溃成为 `orphaned`（见 5.7）。
- 不排队：并发达到 `maxConcurrent` 时，新任务直接受理失败（返回"当前异步任务已满"文本给模型，模型自行决定是否稍后重试或同步做）。

### 5.4 AsyncTaskRegistry 与落盘顺序

新类型 `AsyncTaskRegistry`（建议放 `Core/`，两种模式与 Host 图片都能引用）：

```csharp
public sealed record AsyncTaskRecord(
    string TaskId,
    string Kind,            // 任务类型，如 "rule-summary"
    string ParticipantId,   // 发起者；可为 null（Host 侧触发）
    string SessionId,       // 会话目录，用于落盘定位
    DateTimeOffset CreatedAt,
    int TimeoutSeconds,
    string Status,          // running | completed | failed | cancelled | orphaned
    string? ResultRef,      // 结果文件相对路径
    string? ResultDigest,   // ≤200 字，投递用
    string? ErrorCode,
    string? ErrorMessage,
    long WallMs);
```

落盘：`<会话目录>/async-tasks.jsonl`，append-only。

**顺序纪律（继承 B5 教训，逐条可证）**：

1. 受理：先写 `async-tasks.jsonl`（`running`）→ 再发 `async-task.started` → 最后把受理凭证文本返回给模型。
2. 完成：先写结果文件（`ResultRef`）→ 更新 `async-tasks.jsonl`（`completed`）→ 再发 `async-task.completed`。**订阅方（投递面）收到事件时，磁盘上一定已经能看到结果。**
3. 失败：更新 `async-tasks.jsonl`（`failed` + error）→ 再发 `async-task.failed`。
4. 取消/超时：更新状态 → 再发事件。

### 5.5 工具接入契约（受理凭证）

工具实现方（如 `generate_rule_summary`）的同步段只做：参数校验 → 调 `registry.Start(...)` → 拿回 `taskId` 与受理状态 → 构造 `FunctionResultContent` 返回。

返回给模型的受理文本**固定形状**（模型可预期）：

```
已受理异步任务 <taskId>（<kind>）。完成后我会收到通知，当前无需等待。
```

- 受理失败（关闭/已满/参数非法）返回明确原因文本，模型决定下一步。
- `StepLoop` **零改动**：它把这段文本当普通工具结果加进 `conversation`；模型随后可以结束 step 或继续做别的事。
- 工具内发起后台任务用 `Task.Run` + Linked CTS（注册表持有取消源），**不得**把 CTS 泄漏进 `StepLoop` 的 `cancellationToken`（那个 token 在 turn 结束时就会取消，而任务要活过 turn）。

### 5.6 结果投递（分模式）

投递面是 `SessionCore` 级的一个小订阅者（或各自外壳订阅 `async-task.completed/failed`），**事件驱动、与发起 turn 完全解耦**。

**会议模式**：

- 发起者此刻 `IsRunning == true` → 走定向 steer：`_interrupt.Request(SteerNotice("异步任务完成", $"[异步任务完成 {taskId}] {resultDigest}", now))`，由打断泵合并后 `TrySteer`（复用 4.8 新增的 `SteerParticipantAsync`）。
- 发起者不在运行 → 记入 `_pendingAsyncResults[participantId]`（按参与者聚合，最新一条覆盖，避免积压），下一次 `RunParticipantAsync` 发起时把挂起结果并进 `task` 文本（"另外，你之前发起的异步任务 <taskId> 已完成：<digest>"）。
- `failed` 同样投递：文本改为"异步任务 <taskId> 失败（<code>）：<message>。除非用户要求，不要自动重试。"

**叙事模式**：

- 无 InterruptPolicy，投递 = 追加时间线 `note` 行（`AppendNote(author: 发起者或 "system", text: "[异步任务完成 …]"））+ 广播 `roleplay.line`（导演可见）。
- 下一次任何角色 `CreateComposer` 的 L2 重建自然包含该行；`recall_story` 的 `Kinds` 白名单加 `note`。
- 不打断正在进行的 turn——叙事是时序接话，注入会在下一幕生效，语义正确。

### 5.7 取消 / 超时 / 崩溃恢复

- **取消**：`SessionCore.DisposeAsync` / `MarkEnded` 时 `registry.CancelAll("会话已结束")` → 后台任务经 Linked CTS 收到取消 → 任务侧把状态写 `cancelled` → 发 `async-task.cancelled`。已完成的结果文件不删（数据无价）。
- **超时**：注册表按 `TimeoutSeconds` 挂 `CancellationTokenSource`（同 `PendingDecisionRegistry` 的计时器模式）→ 到期写 `failed(code=timeout)` + 发事件 + 取消后台任务。
- **崩溃恢复**：会话装配时扫描 `async-tasks.jsonl`，把遗留 `running` 记录标 `orphaned`（发 `async-task.orphaned` 或仅日志，第一版只日志），**不自动续跑**——自动续跑会引入"重放副作用"这一整类问题。

### 5.8 配置

`meetingroom.json` 新增顶层段（`MeetingRoomOptions` 加 `AsyncTaskOptions AsyncTasks`）：

```json
"asyncTasks": {
  "enabled": true,
  "defaultTimeoutSeconds": 300,
  "maxConcurrent": 2
}
```

- 校验：`defaultTimeoutSeconds ≥ 1`、`maxConcurrent ≥ 1`，非法值拒绝启动。
- `enabled=false` 时工具返回"异步任务已关闭（asyncTasks.enabled = false）"，不落盘、不发事件。

### 5.9 事件契约

| 事件 | 载荷 | 说明 |
| --- | --- | --- |
| `async-task.started` | `{ taskId, kind, participantId, sessionId, timeoutSeconds, createdAt }` | 受理成功 |
| `async-task.completed` | `{ taskId, kind, participantId, resultRef, resultDigest, tookMs }` | 完成（先落盘后发） |
| `async-task.failed` | `{ taskId, kind, participantId, code, message }` | 失败/超时 |
| `async-task.cancelled` | `{ taskId, reason }` | 会话结束导致取消 |
| `async-task.orphaned` | `{ taskId }` | 启动时发现的崩溃残留（第一版可只发日志） |

前端第一版不做 store 归约（`roleplay.line` 已让导演看到叙事侧结果；会议侧结果进讨论区走既有 `message.committed` 或 `interrupt.applied`）。

### 5.10 首个接入方建议

优先接 **"规则摘要增强版"**（规则摘要质量偏低，要更好得调一次模型）：它天然满足"长耗时、结果可稍后到达、发起者是说书人"三个条件。次选：地图区域描述预生成（`MapSectionFor` 的模型增强版）。

### 5.11 验收标准（probe + 真机）

1. [受理即落盘] 工具调用后返回文本含 `taskId` → 立刻读 `async-tasks.jsonl`，该 `taskId` 的 `running` 记录已在。
2. [完成顺序] 任务完成后：`async-tasks.jsonl` 里 `completed` 先于 `async-task.completed` 事件（探针按文件内容与事件时间先后断言）。
3. [会议-运行中投递] 发起者 turn 运行中任务完成 → 收到 `interrupt.applied`（kind=steer）且该 turn `SteerCount > 0`。
4. [会议-空闲投递] 发起者空闲时任务完成 → 下一次 `RunParticipantAsync` 的 task 文本含 `resultDigest`（探针断言注入文本）。
5. [叙事投递] 任务完成 → `roleplay.line` 一条 + 时间线多一条 `note` → 下一轮说书人上下文 L2 含该行。
6. [超时] `defaultTimeoutSeconds=1` 的测试任务 → `async-task.failed(code=timeout)`。
7. [取消] 任务运行中结束会话 → `async-task.cancelled`，后台任务退出，无遗留 `Task`。
8. [前缀指纹不变] 受理凭证只进发起者私有 `conversation`，不进共享节；开关该功能前后前缀指纹一致。
9. [关闭] `asyncTasks.enabled=false` → 工具返回关闭文本，无落盘、无事件。

## 7. 风险与未决

- **watchdog 误判**：`suspect_drift` 自动干预会把剧情带偏 → 第一版 drift 只提醒（已在 4.7 定）。若实测误判率高，降级为"全部只提醒"。
- **watchdog 成本**：每次判定一次小请求。默认周期保守（会议每 3 轮 / 叙事每 6 个 revision），且冷却 2 周期；实测太贵可再调稀或改"仅事件触发"。
- **注入导致前缀 miss**：watchdog 纠偏与异步结果投递走 steer，必然让该参与者下一 turn 前缀 miss——这是既有语义（`_steeredSinceLastTurn` 已能归因），不是新风险；但要控制注入频率（冷却 + 覆盖式待投递队列）。
- **叙事时间线混入 `note` 行**：影响 L3 压缩（`CompressHistory` 按行压缩）与 `recall_story` 过滤。已在设计里定：`note` 进 `Kinds` 白名单，压缩时按普通行处理（它很短）。
- **未决 1**：watchdog 是否值得独立 `model`（默认跟随 `provider.model`，先不做独立配置解析之外的逻辑）。
- **未决 2**：`async-tasks.jsonl` 放会话目录还是工作空间目录。本设计定"会话目录"（任务属于会话）；若将来有跨会话任务再迁。
- **未决 3**：Part B 的 `ResultDigest` 由谁生成（任务自身返回 ≤200 字摘要，第一版由任务实现方负责截断，不做二次模型摘要）。
