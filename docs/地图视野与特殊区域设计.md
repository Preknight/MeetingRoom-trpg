# 地图视野、迷雾与特殊区域设计

> 状态：设计稿（2026-10-28 00:35），尚未实施。
> 前置文档：[`地图编辑器设计.md`](地图编辑器设计.md)（M1–M4 已落地）、[`战斗托管设计.md`](战斗托管设计.md)。

## 0. 这一版要解决什么

现有地图能用（底图 + 网格 + 墙/房间 + token），但它是按"**只有说书人知道空间**"设计的：
角色 Agent 拿不到地图段（`MapSectionFor` 对非说书人返回空串），更没有图像输入，只能从正文里推断空间。

这一版把它推进到"**DM 与角色都能看图，且看到的是各自该看到的那一份**"：

1. 主界面加地图编辑器入口；
2. 绘制支持 `Enter` 结束；
3. 区分**底图模式**与**手绘模式**：有底图时墙/房间退为结构标注，没有底图时它们就是场景；
4. **迷雾**：**三态**（未探索全黑 / 已探索半透明 / 当前视野全亮），按格绘制；默认整张图全黑，DM 按需揭开；
   **只有 DM 能改**，说书人只能提议；
5. **特殊区域**：多边形或圆形，带类型与备注（法术范围、困难地形、传送门……）；
6. **多模态**：把"该视角的叠加图"作为图像输入交给模型，网格算距离；
7. **双端分工**：编辑器是 DM 视图（可写），叙事页战术板是玩家视图（只读），改动实时同步。

## 1. 现状 vs 目标

| 维度 | 现状（2026-10-27） | 本设计目标 |
| --- | --- | --- |
| 入口 | 只能手输 `/map-editor` | 顶栏「地图」按钮 |
| 结束绘制 | 墙双击、房间点回起点 | 两者都保留，另支持 `Enter` |
| 场景来源 | 只有墙/房间（无底图则空） | 底图模式 / 手绘模式并存 |
| 玩家视野 | 只按 `token.visible` 过滤 | 叠加迷雾遮罩 |
| 迷雾 | 无 | 按格绘制、DM 可擦、说书人只能提议 |
| 区域 | 房间（name + light） | 新增 `zones`：多边形/圆形 + 类型 + 备注 |
| 角色拿到地图 | 拿不到（本地地图只给说书人） | 视觉可用时拿"自己视角的图"；不可用时拿文字段 |
| 图像输入 | 无 | `GET /api/maps/{id}/view` 合成的 PNG |
| 距离 | 说书人用【地图】文字段 | 双方都用网格 + 图；文字段降为补充 |

## 2. 数据模型

地图文档 `maps/<id>.json` 扩展三处（旧文档全部兼容，新字段都有默认值）：

```jsonc
{
  "id": "map-ab12cd34ef56",
  "name": "地下墓室",
  "mode": "image",              // 新增：image = 有底图，sketch = 手绘（无底图）
  "image": { "file": "map-ab12cd34ef56.webp", "width": 4096, "height": 2784 },  // sketch 模式下为 null
  "grid": { "dpi": 81.5, "offsetX": 16, "offsetY": 64, "type": "square", "feetPerCell": 5 },

  "tokens": [{ "id": "ella", "name": "Ella", "x": 1278.18, "y": 1039.83, "visible": true }],
  "walls":  [{ "id": "w1", "points": [[100, 100], [900, 100]], "kind": "wall", "open": false }],
  "rooms":  [{ "id": "r1", "points": [[994, 797.5], [1564.5, 1287]], "name": "储藏室", "light": "bright" }],

  // 新增：迷雾。三态：未探索（全黑）/ 已探索（半透明）/ 当前视野（全亮）。
  // 格子索引（不是像素）——标定一改，像素会漂，格索引不会。
  // 默认整张图**全黑**（等价于“一开始涂满所有格子”），但用空集表示，不存 1700 条记录。
  // 约束：visible ⊆ explored（服务端写入时强制）。
  "fog": {
    "enabled": true,
    "explored": [[12, 9], [13, 9], [12, 10]],   // 见过：半透明
    "visible":  [[12, 9]]                        // 当前在视野：全亮
  },

  // 新增：特殊区域
  "zones": [
    {
      "id": "z1",
      "name": "油腻术",
      "kind": "spell",                    // spell | terrain | portal | hazard | custom
      "shape": { "type": "circle", "center": [1200, 900], "radiusCells": 3 },
      "color": "#c9a227",
      "note": "DC 13 敏捷豁免，失败倒地",
      "visible": true                     // false = 只给 DM 看
    },
    {
      "id": "z2",
      "name": "传送门",
      "kind": "portal",
      "shape": { "type": "polygon", "points": [[300, 300], [420, 300], [420, 420], [300, 420]] },
      "color": "#7b61ff",
      "note": "通往二层祭坛",
      "visible": false
    }
  ]
}
```

约定：

- `mode` 由 `image` 是否存在推导（有 `image` → `image`，否则 `sketch`），显式字段只用于兼容历史数据；
- `fog` 用三态：`explored`（见过，半透明）与 `visible`（当前在视野，全亮）；**两者都不在 = 未探索（全黑）**。
  格子索引整数对 `[gx, gy]`，换算：`gx = floor((x - offsetX) / dpi)`。默认两张表都为空 = 全图全黑，
  等价于“一开始涂满所有格子”，但不必存 1700 条记录。`visible ⊆ explored` 由服务端强制；
- `zones[].shape` 二选一：`polygon`（像素坐标点集）或 `circle`（圆心像素 + 半径格数）；
- `kind` 是受控词表，`custom` 时靠 `name` 表达；`note` 自由文本，进上下文时原样给模型。

## 3. 交互设计

### 3.1 入口

主界面顶栏按钮组加「地图」（`<a href="/map-editor" target="_blank" rel="noopener">`）。
新标签打开——切走再回来不该丢掉当前会话与流式状态。

### 3.2 结束绘制

| 动作 | 现有 | 新增 |
| --- | --- | --- |
| 画墙结束 | 双击 | `Enter`（等价） |
| 画房间闭合 | 点回起点 | `Enter`（≥3 点有效） |
| 取消 | `Esc` | 不变 |

`Enter` 在表单输入框内不触发（房间属性 / 区域属性表单里 `Enter` 只做「确定」）。

### 3.3 工具与快捷键

工具条扩为：`选择 / 画墙（墙·门·窗）/ 画房间 / 迷雾 / 特殊区域`，外加原有的吸附、撤销、重做、删除。

数字键切换工具：`1` 选择、`2` 画墙、`3` 画房间、`4` 迷雾、`5` 特殊区域（在输入框内不生效）。

### 3.4 迷雾三态工具

迷雾是**三态**，工具也按三态设计：

| 子工具 | 动作 | 适用场景 |
| --- | --- | --- |
| **揭示**（笔） | 黑 → 半透明：格子加入 `explored` | 玩家走到一处，DM 把它标成“见过” |
| **视野**（笔） | 半透明 → 全亮：格子加入 `explored` + `visible` | 标记“此刻正被看见”的区域 |
| **遮黑**（橡皮） | 任意 → 黑：从 `explored` 与 `visible` 移除 | 撤回误揭、或让玩家重新失去视野 |

- 三支笔都是按住拖动，经过的格子按格去重、拖动过程中不重复写；
- 切换：工具条「迷雾」给三个二级按钮，或键盘 `4` 进入迷雾后再按一次循环三态；
- 未标定（`grid.dpi <= 0`）时三个子工具都禁用并说明原因——没有格就没有格索引；
- 结果立刻可见：DM 视角只画边界（不遮内容），玩家视角按三态着色（见 §4）；
- 一次拖动结束后自动保存（`PUT /api/maps/{id}/document`），不必单独点「保存迷雾」。

### 3.5 特殊区域

- 工具「特殊区域」→ 选形状：
  - **多边形**：点击加点，`Enter` 或点回起点闭合（同房间）；
  - **圆形**：点圆心 → 弹表单填半径（格数，默认 2，上限 12）；
- 落定后弹「区域属性」表单：名称、类型（法术 / 地形 / 传送门 / 危险 / 其他）、备注、颜色、**对玩家是否可见**；
- 选中已有的区域可以改属性或删除（与房间/墙一致的选中语义）。

### 3.6 DM 调整迷雾的三条路径

1. **编辑器里刷**（主路径）：三支迷雾笔（揭示 / 视野 / 遮黑）；
2. **叙事页战术板快速刷**（M6 后期，可选）：DM 视角下给同样的三支笔，直接 `PUT /api/maps/{id}/document`；
3. **说书人提议 → DM 确认**（§3.7）。

都只要求“界面上区分视角”——当前是单用户工具，DM 就是用户本人，不做鉴权。

### 3.7 说书人只能提议

新增工具 `propose_reveal_fog`，参数二选一：

```jsonc
{ "cells": [[12,9],[13,9]] }                       // 按格建议揭示（→ explored）
{ "shape": { "type": "circle", "center": [1200,900], "radiusCells": 2 } }  // 按区域建议揭示
```

走 `propose_world_state` 同一套确认通道：生成 pending decision → DM 同意后由**服务端**把对应格子加入 `explored`
（**不直接设成 `visible`**，`visible` 只由 DM 判断“此刻是否真的在视野内”）→ 推 `roleplay.state`。
DM 拒绝或超时一律不生效——这里的超时默认必须是“不揭示”，与“超时按默认选项”的既有约定例外。

理由：迷雾是信息闸门，一旦说书人能自己揭开，`MapSectionFor` 里“角色只能看到该看的”就失效了。

## 4. 渲染规则

前端按视角渲染（`board.js` 增加 fog / zones 图层）。迷雾三态在两种视角下的表现不同：

| 迷雾状态 | DM 视角 | 玩家视角 |
| --- | --- | --- |
| **未探索**（不在两表里） | **黑 35% 遮罩 + 边界线**（不遮死，仍能看清底图，但一眼能看出哪块没揭） | **纯黑不透明** |
| **已探索**（在 `explored`） | 不额外绘制 | 黑 65% 叠加底图：能看出地形轮廓，看不清细节 |
| **当前视野**（在 `visible`） | 细边框标出范围 | 原图正常亮度（可加一圈极淡高光） |

> DM 视角的 35% 遮罩是刻意保留的：只画边界容易漏看——大面积未探索区域里一条细线很不显眼，
> DM 会误以为那块已经画过了。35% 既能看出“这里没揭开”，又不影响描墙描房间。

其余元素：

| 元素 | DM 视角 | 玩家视角 | 说明 |
| --- | --- | --- | --- |
| 底图 | 原图 | 原图 + 迷雾遮罩 | sketch 模式用纯色底 |
| 网格 | 显示 | 显示 | 未探索区里的网格也被遮掉 |
| 房间 | 全显示（fill + 名称 + 光照色） | 同 DM，但落在未探索格里的部分被黑盖住 | 房间本身不是秘密，可见性交给迷雾 |
| 墙 | 全显示 | 同上 | |
| token `visible=false` | 虚线边框 | 不渲染 | 现状已如此 |
| zone `visible=false` | 显示 | 不渲染 | 新增 |
| zone `visible=true` | 半透明填充 + 名称 | 同 DM（被迷雾遮住的格仍遮住） | 颜色区分类型 |

实现建议：迷雾用一张 `<canvas>` 或 SVG `<path>` 一次性拼出所有格子（避免 1700 个 `<rect>`），
三态分别用 `#000`、`rgba(0,0,0,.65)`、不绘制，用 `pointer-events: none` 让点击穿透。

### 4.1 双端同步：编辑器是 DM 视图，战术板是玩家视图

- **编辑器（`/map-editor`）= DM 视图，也是唯一写入口**：能看全图、能改墙/房间/token/迷雾/区域；
- **战术板（叙事页）= 玩家视图，默认视角改为「玩家」**：只读展示，就是给玩家看的那块板；
  仍保留「视角：DM / 玩家」切换，方便 DM 自己核对；
- **同步链路（已存在，本设计复用）**：编辑器一次改动 → `PUT /api/maps/{id}/document` →
  `NotifyMapChanged()` → `PublishState()` → 叙事页 SSE 收到 `roleplay.state` → 战术板重绘。
  实测 PUT 到快照到达 **< 80 ms**（M4 验收），迷雾改动走同一条链路，所以“DM 擦一块，玩家那边立刻亮”；
- 两个页面可以是**两个标签同时开着**：编辑器不订阅 SSE，它自己写完就重画；战术板靠 SSE 更新，断线重连后由快照重建；
- 注意：战术板切到「玩家」视角时**不显示** `visible=false` 的 token 与 zone，也不显示未探索区域——
  这样“给玩家看的屏幕”可以安全地投出去。

## 5. 模型侧：多模态

### 5.1 谁看到什么

| 模型 | 图像输入 | 结构化输入 |
| --- | --- | --- |
| 说书人 | `dm` 图：整图、**不带任何迷雾**、含隐藏元素区域 | 现有全量文字段（房间、墙、距离、参照物） |
| 角色 | `player` 图：**覆盖已探索区域的外接矩形**、只叠**纯黑**未探索迷雾 | 自己的位置、周围可见 token 与距离、已探索但当前不可见的区域、脚下特殊区域 |

关键约定：**图只负责“地形长什么样”，动态信息不进图**。

- 图里**不画 token**、**不画灰色（已探索）迷雾**——这两类数据每轮都在变，画进图里会让缓存永远失效；
- token 位置、灰雾范围、距离用**结构化文字**给（`MapSectionFor` 的角色视角段），或给角色一个查询工具（§5.5）；
- 因此 `player` 图在同一版文档下**所有角色共用一张**，缓存命中率极高。

### 5.2 图的生成（ImageSharp）

新增只读端点：

```
GET /api/maps/{id}/view?mode=dm|player&maxPx=1024
→ image/png
```

- 服务端合成（ImageSharp，纯托管）：底图（或 sketch 模式的纯色底）→ 网格细线 → **纯黑迷雾**（未探索格）
  → 房间/墙细线 → 区域半透明填充。**不叠 token、不叠灰雾**（理由见 §5.1）；
- 覆盖范围：
  - `player`：**已探索区域的外接矩形**（`explored ∪ visible` 的最小包围盒，四周留 1 格余量）；
    一个已探索格都没有时**不出图**（返回 204），角色只看文字；
  - `dm`：整图（DM 需要全局，且 DM 图不带迷雾）；
- 缩放：长边不超过 `maxPx`（默认 **768**，可配 512–1024），**只做一次统一缩放，不按角色裁剪**——裁剪会让每角色的图都不同，缓存全废。
  实测 token 成本（2026-10-28，纯色图）：64/256/512 边长都是 **191**（有最低档），1024 → **659**，2048 → **1001**。
  所以 768 附近大约落在 191–659 之间，性价比最好；**不要直接送 4096 原图**（估计 1500–2000+）。
- 缓存：键 `(mapId, revision, mode, maxPx)`，内存 LRU（容量 8，够 dm/player × 几档尺寸）；
  文档一改 revision 递增，旧图自然淘汰；
- 依赖：**ImageSharp 3.x**（已定）。许可为 Six Labors Split License：个人 / 开源免费，
  商业用途超过营收阈值需付费——本项目按个人项目使用，若将来商用需重新评估。
  M8 开工前确认开发环境 NuGet 能离线还原 3.x。

### 5.3 上下文接入

- `ContextComposer` 的 `ComposeRequest` 增加 `Images: [{ mediaType, bytes, caption }]`；
- 图片放**角色节**（逐轮变化），绝不能进共享节——否则前缀缓存每轮 miss；
- 由于图不含 token / 灰雾且按文档 revision 缓存，**同一版文档下每轮拿到的是同一张图**，
  跨轮、跨角色都命中；真正变化的只有结构化文字段；
- 成本：1024px PNG ≈ 2k–3k tokens/次/角色。控制手段：
  - `vision.enabled`（默认 **false**）、`vision.maxPx`；
  - `vision.onlyOnChange`（默认 true）：文档 revision 没变时复用上一轮图片引用，不重复附图；
- **前置校验**：`provider` 必须具备图像输入能力。M8 第一步就是拿当前 provider 实测一张图能否被接受。
  **不做文字回退**——若模型不接受图像输入，直接报错并提示用户更换支持视觉的模型（见 §5.4）。

### 5.4 视觉能力不可用时：报错并提示换模型

**不做回退。** 地图的可见性语义（迷雾、谁看到什么）依赖图像输入；一旦回退成纯文字，等于换了一套
信息模型，两套并存会让“看到的”和“以为看到的”对不上。

处理方式：

- **启动时探测**（`vision.enabled=true` 时）：向 provider 发一次**颜色回读**探测，而不是只看 HTTP 状态。
  2026-10-28 实测（见 §14）：`deepseek-v4-pro` 收到图**返回 200**，但正文为空、推理里写“图片是 [Unsupported Image]”——
  **静默失明**。只看状态码会把这种情况当成“支持”。所以探测必须是：
  发一张已知纯色（例如纯红 8×8）的小图，问“这张图是什么颜色？”，
  **答对才算支持**；答错、答“看不到”、正文为空、或 400 → 一律判定不支持 → **拒绝启动**并写清：
  `当前模型 <model> 不接受图像输入（探测回读：<实际回答>），地图视觉需要支持视觉的模型，请在 meetingroom.json 里更换 provider.model`；
- **运行时兜底**（探测通过但实际调用仍被拒或被判“看不到”）：该轮不附图，但**在警告通道发出明确提示**
  （沿现有 `roleplay.warning` 通道）：`地图视觉本轮未生效（模型未读到图），请检查 provider.model`，
  不静默降级、不假装成功；
- `vision.enabled=false` 是**用户主动关闭**视觉（此时行为与现在一致：只给文字段），与“模型不支持”是两件事，
  两者不可混淆。

> 原来设想的“角色视角文字段”仍然保留，但它的定位是**独立能力**（让模型知道自己周围有什么），
> 不作为视觉不可用时的替代品——见 §5.5 与 M9。

> 也就是说：§5.4 是 M8 之前的兜底，甚至可以单独作为一批提前落地。

### 5.5 角色侧工具集（已定）

角色 Agent 目前完全没有工具（`IsNarrator ? Tools : []`）。本设计给它一小组**只读 + 只请求**的工具。

先说它拿到的**结构化文字**（独立能力，与视觉无关，M9 落地）：由 `MapSectionFor` 在角色节生成，包含
自己的位置、周围可见 token 与距离、已探索但当前不可见的区域、脚下是否有特殊区域。这段文字**不是**视觉的替代品，
而是与图并行的另一条信息通道——图答“地形长什么样”，文字答“谁在哪、多远”。

工具清单：

| 工具 | 参数 | 作用 | 性质 |
| --- | --- | --- | --- |
| `look_around` | `characterId?`、`radiusFeet?` | 看周围有谁、多远（背后按该角色视角过滤） | 只读 |
| `check_terrain` | 无 | 脚下/周围有没有区域效果、是否困难地形、雾是否挡住 | 只读 |
| `dice_roll` | `who`、`expression`、`mode?`、`reason?`、`dc?` | 自己掷一次骰（数值由程序产生） | 产生数值，不改变世界 |
| `request_judgement` | `skill?`、`ability?`、`kind?`、`dcHint?`、`reason` | **请求**一次判定：例如“想查这扇门有没有魔法陷阱，请做一次奥秘检定” | 只请求，不执行 |
| `request_combat_action` | `kind`、`targetId`、`weaponId?`、`spellId?`、`intent`、`reason?` | **请求**一次战斗动作：例如“想偷袭背对我的敌人” | 只请求，不执行 |

三条硬约束：

1. **请求工具不产生任何结算**。真正的 `request_check` / `combat_action` 仍然只有说书人能调——
   角色说“我要偷袭”，说书人决定这是不是偷袭、算不算优势、掷什么骰。角色永远不能自己写结果。
2. **请求要落盘可见**。角色调 `request_*` 会写一条 `story.jsonl` 记录（`kind=request`，
   含 `requestKind=check|combat_action`、建议的技能/动作、`reason`），并在剧情流里显示一行
   “（Ella 请求：对门做一次奥秘检定）”。说书人下一轮复盘时从 `SpokenContext` 里看到它，
   决定执行（调 `request_check` / `combat_action`）或叙事化解（“门上没有魔法痕迹，不必掷骰”）。
3. **拒绝要给理由**。说书人不采纳请求时，正文里要说明为什么（否则角色会反复请求）。

**后续可能加 DM 审批**：`request_*` 产出的记录是 pending decision 的天然载体——将来若要“DM 逐条批准”，
把这条记录从“说书人自行决定”改成“等 DM 确认”即可，工具签名不用变（预留 `requiresApproval` 开关）。

**明确不给角色的工具**：`propose_world_state`、`nudge_character`、`idle_beat`、`declare_scene_end`、
`ask_user`（话说人的控场权）、`start_combat`、`next_turn`、`end_combat`、`combat_action`、`request_check`
（结算权）、`dm_override`、`propose_reveal_fog`（DM 专属）。

**架构影响（必须提前知道）**：角色从“单轮文本生成”变成“可调用工具的多步回合”，
复用 `AgentSession` 的工具循环并受 `limits.maxStepsPerTurn` 约束。代价是：
每个角色多一份工具 schema 的 token、多步往返的延迟；所以角色工具描述必须一句话说完，工具集也别再加。

## 8. 风险与待定项

1. **provider 视觉能力**（M8 的前置）：**已验（2026-10-28，§14）**——`deepseek-chat` 支持图像输入
   （服务端路由到 `deepseek-flash`，三种颜色回读全对）；**`deepseek-v4-pro` 返回 200 但看不到图**（静默失明），
   必须避开；不存在 `deepseek-vl2` 这类专用视觉模型名。若不满足（用户换了模型），
   **不降级、不退回文字**：报错并提示更换支持视觉的模型（§5.4）。
2. **ImageSharp 3.x 的许可**：Six Labors Split License（个人 / 开源免费，商业超阈值需付费）。
   开发环境 NuGet 需能离线还原 3.x，否则 M8 开不了工。
3. **每轮附图成本**：1024px 图约 2k–3k tokens/次/角色；因图不含 token/灰雾、按 revision 缓存，
   同一版文档下跨轮命中，所以主要成本是“文档一改就要重传一次”，而不是每轮都付。
4. **角色改为多步工具回合的代价**：角色从“单轮生成”变成“可调工具的多步循环”，
   每个角色多一份工具 schema 的 token 与多步往返延迟；工具描述必须一句话，工具集不再扩充。
   另外说书人工具面会因新增 `propose_reveal_fog` 变化，角色前缀会因工具集变化——都是预期的一次 miss。
5. **迷雾体量**：三态用“两张已揭示表”表示，未探索不存数据，所以空图 0 条；全探索约 1700 条
   （50×34 格），JSON 约 15 KB，可接受；超过阈值再考虑位图 / RLE 编码。
6. **单用户假设**：`roleplay.state.map` 会把 `fog` 全量下发，前端按视角渲染。将来多客户端（玩家各带屏）时
   必须在服务端按身份裁剪，否则凡能拿到快照的人都能看到全图。
7. **战术板默认改玩家视角的连带影响**：DM 自己看全局要切回 DM 视角；现有验收里断言
   “token 数 = 3（含隐藏）”的用例需改成在 DM 视角下跑。
8. **角色看图的闸门**：`player` 图按已探索区域出图，裁剪不再是逐角色的——所以“信息闸门”主要靠迷雾数据，
   而迷雾只能 DM 改；这是比“按半径裁剪”更可靠的闸门，但要求 DM 真的及时遮黑。
7. **`propose_reveal_fog` 会动工具面指纹**（`22998d92…` 将变），属预期的一次 cache miss，需同步更新 `PromptPrefixVersion` 与文档基线。
8. **`MapSectionFor` 的注释歧义**：现有注释写“说书人拿全量、角色拿半径内”，但本地地图分支实际只给说书人。M9 改这块时应顺手订正注释，避免后续误读。

## 10. 实施记录（M6a：迷雾基础——数据 + 三支笔 + 渲染，2026-10-28 02:00）

**范围**：数据模型、编辑器三支笔、`board.js` 三态渲染。**不含** `zones`、不含 `propose_reveal_fog`（M6b）、不动提示词与工具。

### 10.1 数据模型

```jsonc
"fog": { "enabled": true, "explored": [[12,9]], "visible": [[12,9]] }
```

- `MapFog(bool Enabled = false, GridCell[]? Explored, GridCell[]? Visible)`，`GridCell` 是 `[gx, gy]` 整数对
  （自定义转换器，写出来就是两元素数组）；`Disabled` = `false + 两表为空`（= 整张图全黑，不存上千条记录）；
- `MapDocument.Fog` 与 `MapAsset.Fog` 都**可选**，旧文档缺字段 → `MapFog.Disabled`，不用迁移；
- **写入校验**（`MapDocumentValidator.ValidateFog`）：
  - `visible ⊆ explored` → 否则 400 `迷雾不一致：视野格 [2,2] 不在已探索里…`；
  - 格索引非负、不越出画布换算的网格 → 400 `迷雾格 [99,99] 超出画布（网格 20×15）。`；
  - 没有标定（`dpi <= 0`）时不做越界判断（没有格就没有边界）；
- `GET/PUT /api/maps/{id}/document` 带上 `fog`；`roleplay.state.map.fog` 是**同一份投影**（`MapProjection` 直接读它）。

**顺手修的**：`MapFog` 的两个计算属性（`ExploredCells` / `VisibleCells`）一开始会被序列化出来
（`exploredCells` / `visibleCells` 混进 JSON），加了 `[JsonIgnore]`；`Disabled` 也从 `new()` 改成显式两空表，
否则 `explored: null` 与设计稿的 `[]` 不一致。

## 12. 实施记录（工具参数容错 + 单工具出错不吞回合，2026-10-28 02:30）

### 12.1 r15 的现场

```
tool.call propose_reveal_fog args.shape = "{\"type\":\"circle\",\"center\":[0,0],\"radiusCells\":2}"   ← 字符串，不是对象
participant.status failed
roleplay.error { code: "say", message: "shape 期望一个数组" }
```

模型把结构化参数**序列化成了 JSON 字符串**；dispatch 端按数组/对象解 → 抛异常 →
`SayAsync` 的 `catch (Exception)` 一口吞掉 → **整回合静默消失**（不写 turn、不重试、日志只有一句 "say"）。
普通句正常出回合（2.4s / 7.4s），只有调到这个工具才消失。

### 12.2 两层修法

**P0-1 参数容错**（`ToolArguments`，`NarratorToolDispatcher` 内的 public 辅助）：

| 参数 | 接受的形状 |
| --- | --- |
| `cells` | `[[gx,gy],…]`、`[{x,y},…]`、单个 `{x,y}`，以及以上任何一种的**JSON 字符串** |
| `shape` | 对象 `{type,center,radiusCells}`、**JSON 字符串**（含双重编码）、`center` 可以是 `[x,y]` 或 `{x,y}` |

- 解析失败**不抛**，返回可读错误：`shape 解析失败，应传 {"type":"circle","center":[x,y],"radiusCells":2}。`；
- 区分"没给这个参数"（合法，二选一）与"给了但解析不了"（报错）——第一版漏了这个区分，
  坏形状被当成"没给"，probe 直接抓出来了。

**P0-2 单个工具出错不得吞掉整回合**：

1. **dispatcher 层**（根因）：`DispatchAsync` 的 switch 包进 `try/catch`，
   任何异常变成工具回执 `工具 X 执行出错：…。检查参数形状后重试，或换个办法。`
   （`OperationCanceledException` 照常上抛）——这是 function calling 的标准行为，模型能自己修正；
2. **`SayAsync` 层**（兜底）：`roleplay.error` 现在带 `turnId` 与 `abandoned: true`，
   不再只有一句 "say"。真正把回合丢掉的路径已经在上游被堵死，这一层只保证"就算还有异常，也能查到是哪一轮"。

### 12.3 指纹（**与预期不同：没有变**）

```
工具面  fc7c5824…（未变）   前缀  2ab6c63a…（未变）
```

原以为"参数类型改动会动工具面"，但实际做法是**只改读取方式、没改参数声明**
（`int[][]?` / `FogShapeArgument?` 保持原样），schema 一个字没动 → 工具面自然不变。
这比预期更好（少一次 cache miss）。

### 12.5 教训

**工具参数形状错 → 整回合静默丢失**：这不是某个工具的 bug，是所有工具的共性风险。
一个 `catch (Exception)` 写在回合级，就把"工具调用失败"升级成了"这一轮白跑"，而且**日志里看不出来**
（只有 `code: "say"` 和一个与工具无关的消息）。原则：**工具层出错必须在工具层变成回执**，
回合级 catch 只兜真正的 provider / 宿主故障。

### 16.2 `MapViewRenderer` 的合成规则

图层：**底图（sketch 用 `#0d1117` 纯色）→ 网格细线 → 纯黑未探索 → 房间/墙细线 → 区域半透明填充**。

**刻意不画两样**：

| 不画 | 理由 |
| --- | --- |
| **token** | 每轮都可能动；画进去图就每轮不同，缓存永远失效 |
| **灰色（已探索）迷雾** | 同上；而且"可见性"的语义由纯黑未探索格 + 文字段表达就够了 |

这不是省略，是设计的核心：图按**文档 revision** 缓存，任何"每轮变的东西"都不能进去。

裁剪与尺寸：

- `mode=dm`：整图，**不叠迷雾**；
- `mode=player`：只画 `explored ∪ visible` 的外接矩形（四周各留 1 格）；
  **一个已探索格都没有 → 返回 null（端点 204）**；
- `grid.dpi <= 0`（未标定）→ null（204）——没有格就画不了网格与迷雾；
- 长边缩放到 `maxPx`（默认 **768**，端点接受 256–2048），**只做一次统一缩放**，不按角色裁剪。

### 16.3 端点与缓存

```
GET /api/maps/{id}/view?mode=dm|player&maxPx=768 → image/png | 204
```

- 缓存键：**`{mapId}|{document.UpdatedAt}|{mode}|{maxPx}`**，进程内 LRU（容量 8，`MapViewCache`）。
  **说明：文档没有独立的 revision 字段**，`UpdatedAt` 在每次 `SaveDocument` 时都会更新，等价可用；
  如果将来加 revision 字段，换成它更好（语义更明确）。
- 文档一保存 `UpdatedAt` 就变 → 旧图自然淘汰，不需要单独失效逻辑。

### 20.1 选的重建方案：(a) 快照带 `requests`

**顺手补的一个洞**：`StoryTimeline.Load` 原来没有 `kind == "request"` 的分支，落盘的请求**重启后就丢了**

### 20.2 去重（"实时一条 + 重放再一条"）

两条路径都会产出请求行：

1. 实时：`roleplay.request` 事件 → append；
2. 重建：`roleplay.state` 快照 → 整份替换。

所以按 **`(actorId, requestKind, summary, at)`** 做 key 合并（`mergeRequests`）,而不是直接追加或替换：
快照里的条目覆盖同 key 的旧条目，**同一时刻的同一条请求只会出现一次**。

还有一条容易漏的：**换会话不能串台**。合并时只在 `payload.storyId === state.roleplay.storyId` 时保留旧切片，
否则从空开始——不然侧栏切到另一场戏，上一篇的请求会挂在新剧情流里。

事件 payload 补了 `at`（原来只有 actorId / requestKind / summary / reason）。没有它，实时行排序落不到正确位置。

### 22.1 P0：interaction 超时计时——**计时器本来就是准的**

先量，再改。新增 `--probe-interaction-timeout`，用 **1 秒超时**（不等 120 秒）：

```
✅ ① registry 1 秒超时实际耗时 ≤ 6s     1003 ms（配置 1000 ms，偏差 3 ms）
✅ ① 超时后走默认选项（reject）        timedOut=True 选中=reject
✅ ② 迷雾提议 1 秒超时实际耗时 ≤ 6s    1018 ms（偏差 18 ms）
✅ ② 超时 = 不揭示（默认 reject）      等导演确认超时，按约定不揭示：1 格保持全黑。
```

链路本身没有可修的地方：`PendingDecisionRegistry.Open` 起的是
`new CancellationTokenSource(TimeSpan.FromSeconds(timeoutSeconds))`，到点回调 `TimeOut` →
`TryComplete(默认选项)` → `RequestDecisionAsync` 的 `await ...WaitAsync` 立刻返回。没有轮询、没有从
`createdAt` 算起。**偏差 3 ms / 18 ms**，远小于要求的 5 秒。

**那 r16 的 260 秒怎么解释**：探针能证明"从挂起到收口"是准的，但不能证明"用户看到的 260 秒"就是这一段。
r17 之后翻历史 `story.jsonl` 里 59 条 interaction 记录，两条 `timedOut: true` 的相邻记录间隔分别是
83 s / 67 s / 203 s —— 203 s 那条前面还挂着一次世界状态提议。**墙钟里含前置回合与上一条交互的等待**，
这与"计时器不准"是两回事。

**能落地的改进是可观测性**：启动时把**实际生效值**打出来——

```
  交互模式：开，等待上限 120 秒
```

下次现场直接对日志，不必靠"我印象里配的是 120"。这也是 `interaction` 段在配置里可以完全不写
（走默认 120）却容易被误记成"配过"的补救。

**没做**：没有拿真实会话再跑一次 120 秒等满来复现 260 秒。要给"260 = 前置回合 + 120"下结论，

### 22.3 P1：区域顶点编辑

墙和房间早就能拖顶点，`zones` 只能改属性 / 删除。现在三种对象共用一套手柄：

- **多边形区域**：每个顶点一个手柄，拖动只改那一个点（吸附规则与墙 / 房间一致）；
- **圆形区域**：**两个手柄**——0 号是圆心（拖动改 `center`），1 号是半径手柄（放在圆心 +x 方向，

  **选的是半径手柄而不是弹表单**：拖动能立刻看到大小变化，也不用多开一层浮层。
- Delete 仍删整个区域；属性表单仍能改名称 / 类型 / 颜色 / 备注 / 可见性。

### 23.1 迷雾**允许**超出底图：边缘冗余 3 格


### 24.2 在底图上按下拖动 → 拖的是图片

### 25.1 进编辑器默认是玩家视角，要点两下才到 DM

**三处叠在一起**（规划会线定位的）：

1. `board.js` 的 `let view = 'player'`（M6a 给叙事页改的默认）；
2. 视角按钮的初始文案**硬编码** `'视角：DM'`——与实际 `view` 相反；
3. `setView(next)` **只赋值**：`view = ...; applyViewport();`——不重绘、不同步文案
   （文案更新只在按钮自己的 click 里写了一份）。

于是：mount → 首次渲染 player → 编辑器随后 `setView('dm')`（内部变 dm，**画面不重绘**，按钮写着 DM）
→ 用户点第一下：dm→player（画面本来就是 player，看不出变化）→ 第二下才真的回到 dm。

**修法**：把三件事收进 `setView` 一个函数：

```js
function setView(next) {
  view = next === 'player' ? 'player' : 'dm';
  viewButton.textContent = `视角：${view === 'dm' ? 'DM' : '玩家'}`;
  applyViewport();
  void render({});
}
```

- 按钮 click 改成只调 `setView(...)`（删掉重复实现）；
- `mount(container, { view })` 新增可选参数，**编辑器传 `{ view: 'dm' }`**——首次渲染就是 DM，
  不再依赖"后面某次 setView"；描述符建好后立刻对齐一次按钮文案；
- 编辑器里那句 `board.setView('dm')` 删掉（初始已给定）；
- 叙事页 `mountBoard(host)` 不传参数 → 仍默认 **player**，行为不变。

### 26.8 追加：底部留白与 rail 表头残留（2026-10-28 15:05）

#### (1) 底部留白：主因不是"缺一行 minmax"，是 `main` 被排进了 auto 行

现象：窗口**拉高**后页面底部大片空白，各列不跟着变高（缩小反而看不出来）。

两层原因，**第一层才是主因**（上一批的猜测只看到了第二层）：

```css
body { display: grid; grid-template-rows: auto auto minmax(0, 1fr); }  /* 顶栏 / 警告区 / 主区 */
.warnings[hidden] { display: none; }
```

1. `#warning-area` 平时 `hidden`（`display:none`）→ **不生成 box、不占格**。自动放置于是把
   `main.workspace` 排进**第 2 行（auto）**，本该给主区的 `1fr` 行空着。
   实测 `getComputedStyle(body).gridTemplateRows` = `40.8px 518.8px 572.4px`，
   main 的 `top=41`、高 `519` —— 它就是第二行，第三行 572px 全空。
2. `.workspace` 只写了 `grid-template-columns`，六个子项都落进**隐式 auto 行**；
   `align-items: stretch` 在 auto 行上拉不出高度（所以即使第 1 点修好，这一层也得补）。

**修法**（`app.css`）：

```css
.workspace {
  grid-row: 3;                              /* 永远落在 body 的 1fr 行 */
  grid-template-rows: minmax(0, 1fr);       /* 六列也落进显式 1fr 行 */
}
```

**读数的坑（上一任在这里误判过）**：留白时 `documentElement.scrollHeight (828) == innerHeight (843)`
看着像"高度链自愈、没有溢出"，其实正是留白证据——内容根本不够高，所以连整页滚动都没有。
判断修没修好要看 **`.workspace` 高度与视口的差**（以及各列高度 ≈ workspace 高度减 padding），
不是 scrollHeight 是否等于 innerHeight。

  `vulnerable` / `conditionImmune` / `traits` / `actions` / `bonusActions` / `reactions` / `legendary` /
  `mythic` / `spellcasting`。`type / size / cr` 仍然可能是 null——**不编默认值**。
- 三个形状不固定的字段用专用归一，不硬套结构：
  - `speed` 可能是 `{"walk":40}`、`{"fly":{"number":60,"condition":"hover"}}`、`{"alternate":…}`、
    `{"choose":…}`、`{"walk":40,"canHover":true}` → `MonsterSpeedConverter` 统一成
    `walk 40、fly 60（hover）` 这样的文本（只用于显示，不参与移动力计算）；
  - `saves` / `skills` 的值可能是数字也可能是字符串 → `FlexibleTextMapConverter` 归一成
    `键 → 文本`；`mastery[] / properties[]` 的元素是 `{uid,note}` → `DescribeObject` 取 `uid`。
- 新增四类：`ClassEntry`（hitDie / saves / spellcastingAbility / skillChoices / subclasses / features）、
  `SubclassEntry`（className / classSource / classRuleset / shortName / featuresInheritedFrom / features）、
  `FeatEntry`、`OptionalFeatureEntry`；特性条目统一 `FeatureEntry`（level / name / cnName / text / references）。
  `references` 形如 `{"type":"refOptionalfeature","id":"Agonizing Blast|XPHB"}`，回执里会点出来
  "这条特性底下还有 N 个可选条目，用 kind=optional 查"。

#### 27.2 两个工具与"权限靠结构保证"

| 工具 | 进哪张表 | 谁能调 |
| --- | --- | --- |
| `lookup_rule` | `Narrator.ToolNames` + `Narrator.CharacterToolNames` | 说书人与角色 |
| `lookup_monster` | **只**进 `Narrator.ToolNames` | 只有说书人 |

`lookup_monster` **不进** `AllToolNames` 的角色子集，也**不写运行时判断**——角色表里根本没有这个名字，
模型连这个工具都看不见。探针用两条反向断言守它：`--probe-character-tools` 检查角色表里
"有 `lookup_rule`、没有 `lookup_monster`"；`--probe-rule-lookup` 再直调 dispatcher 确认
角色拿到的是"只有说书人可以调用 lookup_monster"。

#### 27.3 检索与回执

- 顺序（命中即止）：① `id` / 英文名 / 中文名**全等**（忽略大小写）→ ② `keywords` 任一元素**包含** query
  → ③ 指定了 `kind` 时在同类里搜 `text`。②里命中多条时按名字长度升序排——「火球」的第一条是「火球术」，
  而不是「延迟爆裂火球」。
- 命中多条 → 只列候选（最多 5 条，每条 `名称 | 来源 | 类别`），并提示"用 kind 收窄 / 给更完整的名字"。
- `detail=true` 只给第一条的完整原文（**英文原文**，明确要原文不要翻译）；整体超过 4000 字符截断并标
  `[truncated]`，这个上限对职业 / 子职的全部特性也生效（法师特性合计 7127 字符，实测截到 4012）。
- 紧凑行（示例来自实测）：
  - 法术：`火球术（Fireball） | XPHB | 3 环·塑能` / `施法 1 动作 | 射程 150 尺 | 成分 V,S,M | 持续 立即` /
    `伤害 8d6 火焰 | 豁免 敏捷`
  - 职业：`法师（Wizard） | XPHB | 2024 | d6 | 豁免 INT/WIS | 施法 智力 | 子职 22 个 | 特性 16 条`
  - 子职：`Monk - Drunken Master | XGE | Monk（职业源 XPHB，2024） | 特性 8 条 | 原文继承 PHB`
  - 怪物：`地精武者（Goblin Warrior） | XMM | CR 1/4 | fey · S` / `HP 10（3d6） | AC 15` / `STR 8 15 10 10 8 8`
    / `特性：…`，末尾固定一句「这是模板基线，开战时 DM 可按战况调 HP 与数量」。
- **一个刻意的省略**：豁免只写属性名（`豁免 敏捷`），不写"成功减半"——减半是具体法术的措辞
  （有的写"成功则不受影响"），数据包里没有这个字段，编一个会误导。
- `kind` 接受九个别名与中文（`spell / 法术`、`optional / 可选特性 / 祈唤` …），不认识就明确回
  "不认识的 kind，可选有这些"，不猜。

#### 27.4 限流与边界

- **一轮最多 3 次**（说书人与角色共用）：额度挂在 `NarratorToolDispatcher`，`RoleplaySession.SayAsync`
  每轮开头调 `ResetRuleQuota()`。第 4 次回"本轮的规则查询次数已用完"。
- 查询**不消耗**"一轮一个请求"的额度（那是 `request_judgement` / `request_combat_action` 的事）——
  查资料和提请求是两码事。
- 工具描述里写死了边界：**只读知识，查完不能自己结算伤害与结果，仍要走 `request_judgement` /
  `request_combat_action`（说书人走 `request_check` / `combat_action`）**。
- 规则包没加载 → 回"规则包未加载（rules-data.json）"，不假装成功。

#### 27.5 配置：默认值 + 相对路径按安装目录解析

- `RulesOptions.DataPath` 默认 `data/rules/rules-data.json`（原来是空串 = 不加载）。
- **相对路径按 `PathLayout.InstallDir` 解析**，不按当前工作目录——从别处启动 Host 时 cwd 不是 exe 目录，
  按 cwd 找会静默找不到包。
- 覆盖顺序：配置 → 命令行 `--rules <path>`（新加，Host 启动时也认了，之前只有 `--probe-*` 用）→
  环境变量 `MEETINGROOM_RULES_DATA`。
- **进程内按路径缓存**：4.2 MB / 解析约 80 ms，每开一场会话重解析一次纯属浪费；改成解析一次复用
  （解析失败也缓存，避免每次会话都去读一遍坏包）。**改规则包要重启进程才生效**。

#### 27.8 数据缺口（不是代码问题，下沉给导出侧）

- **200 条子职的 `cnName` 全是空串**——所以「醉拳」这类中文查不到，只能用 `Drunken Master` 或它的 keywords。
  探针因此用英文名验证子职；回执里子职会显示英文名（中文名缺失时不显示空括号）。
- 怪物没有叫 `Goblin` 的条目（XMM 版本叫 `Goblin Warrior`「地精武者」），探针用「地精武者」验证中文命中。
- `export-report.json` 的 `optionalFeatures.byType` 里有 `AI / RN / PB` 等代码，回执里只翻常见几个
  （EI / FS:* / MV:B / AS / MM / RP / ED），其余原样显示代码。

#### 27.9 没做到的

- 没有为规则包做**索引**：每次查询线性扫九节（1800+ 条），实测一次查询 < 20 ms，够用；真成热点再加。
- `lookup_rule` 的正文搜索（③）只在**指定 kind** 时启用，不限类别时不做全文检索——否则「攻击」能命中几百条，
  回执会被候选淹掉。
- 没有在真实会话里让模型自己发起查询（要花 API 调用与真实剧情数据）；探针直调 dispatcher 覆盖了工具层，
  模型"愿不愿意查"仍待真机观察。
