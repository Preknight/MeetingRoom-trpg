# 图片生成模块 · 设计方案（独立附加功能）

> 范围：**图片生成是一个独立附加功能**，在**独立窗口**里由**用户手动执行**，
> 结果**另外保存**，由用户**手动加入角色卡**；"角色卡模块的图片识别能力"留给后续。
> **当前所有 MeetingRoom 相关功能不变，本方案只考虑图片生成模块。**
>
> 因此本文不触碰：编排内核（`SessionCore` / `MeetingSession` / `RoleplaySession`）、
> 上下文装配（`ContextComposer`）、资料状态机（`MaterialStore` 六态）、既有 SSE 语义、
> 既有端点行为。全部改动是**加法**。

配套文档：《[设计方案 - .NET 10 版](Agent%20会议（Meeting%20Room）设计方案%20-%20.NET%2010%20版.md)》（为什么这么设计）。

## 〇、结论：能实现，而且是本项目最省事的那类功能

**能。** 现有 `html 前端 + .NET 10 Minimal API` 架构不需要任何结构改动就能承载它，原因有三：

1. **出网已经是现成的**。项目在用 `OpenAI` SDK 的 `IChatClient`（`OpenAiCompatibleModelFactory`），
   而图片生成只需要一个普通 `HttpClient` POST —— 本模块**不经过** `IChatClient`、不经过 `AgentSession`、
   不经过 step 循环，所以硬约束 5、6、7 天然不参与。
2. **前端是"无构建步骤"的原生 JS + ES modules**，新增一个面板模块 + 一个浮层即可，
   与 `panel-drafts.js` / `panel-path-picker.js` 的形态完全一致。
3. **落盘、路径防护、配置校验、系统文件对话框、事件总线**这五件基础设施都已存在且可复用（见 §一）。

唯一需要实测的外部变量是**网络出口**（Windows 的 PAC 是否被 .NET 的 `HttpClient` 自动采用）——
.NET 侧的行为是支持 PAC 的（见 §七），但必须先实测再动手，故方案把 `--probe-image` 自检排在批 A 第一步。

### 本轮的边界（明确不做）

| 不做 | 为什么 |
| --- | --- |
| **本模块自己的前端**（§九 的独立窗口 / 批 B） | **2026-10 决定暂不实现**：这种"一对一"用法不需要单独界面 —— 命令行与 MCP 工具已经够用。**后端接口全部保留**（见 §十一 批 D、§十四） |

| 回退 / 重生成 / 多候选 | 与叙事模式同一条既有定位（设计文档 §11.4-4） |

## 三、数据模型与存储布局

### 落点：工作空间级 `images/`

```
<工作空间>/
    roles/            # 既有
    materials/        # 既有
    worldbook/        # 既有
    drafts/           # 既有
    meetings/         # 既有
    stories/          # 既有
    images/           # ← 新增
        manifest.json         # 资产清单（原子写）
        refs/<sha256前16位>.<ext>   # 用户导入的参考图（按内容哈希去重）
        out/<id>.<ext>              # 生成结果
```

**为什么放工作空间级而不是会话级**：用户说"结果**另外保存**"并"手动添加到角色卡"，
而角色卡本来就在工作空间根 `roles/`、且**跨会话共享**（设计方案 §15.2 硬规则 2）。
资产与角色卡同层，用户"把图加进角色卡"才不需要跨目录搬东西。
（若日后想改成会话级，只需把 `WorkspaceLayout.ImagesDir` 换成 `SessionDir(...)/images`，
`ImageAssetStore` 的构造参数就是那个目录 —— 一处改动。）

`WorkspaceLayout` 加一个属性并进 `EnsureCreated()` 的数组：

```csharp
/// <summary>图片资产（参考图 + 生成结果）：独立于会话，供用户手动加入角色卡（图片生成模块）。</summary>
public string ImagesDir => Path.Combine(Root, "images");
```

对已有工作空间：`EnsureCreated()` 幂等，下次打开时补建空目录，不动任何既有文件。

### `ImageAsset`（记录，字段与 `MaterialCard` 同风格）

| 字段 | 说明 |
| --- | --- |
| `Id` | `img-0001`（`manifest.NextImageNumber` 顺延，同 `mat-001` 的做法） |
| `Kind` | `reference`（用户导入）/ `generated`（模型产出） |
| `Path` | **相对 `images/` 的路径**，一律正斜杠：`refs/ab12….png` / `out/img-0001.png` |
| `MediaType` | `image/png` 等；以字节嗅探结果为准（见 §六） |
| `Bytes` | 体积 |
| `Sha256` | 内容哈希（参考图按它去重；也给前端做缓存键） |
| `Width` / `Height` | **可空**（不引第三方解码库；能读到就填，读不到留空，界面显示"—"） |
| `Prompt` | 生成用的提示词（参考图为空） |
| `Model` | 生成用的模型 slug（参考图为空） |
| `ReferenceIds` | 本次生成用到的参考图 id 列表（复现依据） |
| `Provider` | `baseUrl` + 模型（便于日后换通道） |
| `Cost` | OpenRouter 回传的 `usage.cost`（可空） |
| `CreatedAt` | UTC |

`manifest.json`（`ImageManifest`）只有 `{ nextImageNumber, images: [] }`，写盘用
`JsonNamingPolicy.CamelCase` + `UnsafeRelaxedJsonEscaping` + `WriteIndented`（与 `MaterialStore` 一致）。

**不变式**（照 `MaterialStore` 的三条硬约束改写）：

1. 任何 `Path` 必须落在 `images/` 内 —— 由 `ImagePathGuard.ResolveWithin` 强制；
2. manifest 先落 `.tmp` 再替换，崩溃不留半截；
3. 文件先落盘、再写 manifest：**文件写入失败不回滚已写好的文件**，manifest 失败时内存与磁盘保持一致；
4. **读者必须显式用 `FileShare.ReadWrite` 打开**——这是本项目已实测过的 Windows 文件共享语义
   （进度文档「风险 9」：写者以 `FileShare.Read` 打开时，读者用默认方式打开会失败，
   表现为"图片明明生成了却读不出来"）。顺序上不会撞（写完文件 + 落 manifest 之后才广播
   `image.generated`，前端此时才请求内容端点），但读取代码仍按这个语义写，
   免得日后加"生成中预览"时被同一个坑绊住。

## 四、HTTP 契约

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/api/images/reference` | **路径导入**：`{ "paths": ["C:/…/ref.png"] }`，路径来自原生对话框或手输 |
| `POST` | `/api/images/upload` | **字节上传**：`multipart/form-data`（字段 `file`，可多个），供拖拽 / `<input type=file>` / 剪贴板粘贴 |
| `POST` | `/api/images/generate` | 发起生成，**立即返回** `{ jobId }`，实际请求在后台跑（同 `POST /api/roleplay/start` 的风格） |
| `GET` | `/api/images` | 资产列表（不含字节）——前端首次连接与刷新用 |
| `GET` | `/api/images/{id}/content` | 返回图片二进制，`Content-Type` 用嗅探结果，带 `Content-Length` 与 `ETag: <sha256>` |
| `POST` | `/api/images/{id}/delete` | 删掉一条资产（**删文件 + manifest 条目**）—— **要做**（2026-10 决定，已从"待定"落定） |
| `POST` | `/api/images/{id}/save-as` | 调系统"另存为"对话框导出（复用 `SystemDialogEndpoints` 的 PowerShell 写法） |

请求体示例：

```jsonc
// POST /api/images/generate
{
  "prompt": "以参考图为准，画一张同一角色的全身立绘，studio lighting",
  "referenceIds": ["img-0001"],      // 可空 = 纯文生图
  "aspectRatio": "1:1",              // 可空 = 用配置默认
  "resolution": "1K",                // 512 | 1K | 2K | 4K
  "quality": "high",                 // auto | low | medium | high
  "n": 1,                            // 1..config.images.maxCount
  "model": null,                     // 可空 = 用配置默认
  "seed": null
}
```

### 参考图进得来：**路径导入**与**字节上传**两条通道

| 通道 | 谁用 | 请求 | 为什么不能只留一条 |
| --- | --- | --- | --- |
| **路径导入** | 浮层里的「用系统对话框选…」 | `POST /api/images/reference` + `{ "paths": [ … ] }` | 复用 `SystemDialogEndpoints` 的原生对话框——**只有它能拿到磁盘真实路径**，且是零字节传输（服务端直接复制文件） |
| **字节上传** | 「选图片…」（`<input type=file>`）、拖拽、`Ctrl+V` 粘贴 | `POST /api/images/upload`（`multipart/form-data`，字段 `file`） | 这三条路**永远拿不到路径**（浏览器安全限制，`SystemDialogEndpoints` 的注释里已写明），只能把字节发给服务端落盘；同时兜住"截图直接粘贴""参考图在浏览器缓存里"的场景 |

两条通道汇到同一个 `ImageAssetStore.ImportAsync(源)`：解析字节 → 校验（类型 / 体积 / 张数）→
按 `sha256` **去重（已存在则复用既有资产，返回 `reused: true`）** → 落 `images/refs/` → 广播 `image.list`。

选型取舍（**推荐统一 multipart**）：上传走 `multipart/form-data` 而不是把图片 base64 塞进 JSON ——
后者会让请求体膨胀约 33%，且要在前端先拼一个很大的字符串（`JSON.stringify` 大对象的内存峰值）。
代价只是 `api.js` 多一个 `postForm` 辅助函数（现有 `postJson` 不动）。

> **实现坑（本项目第一次在端点里收 multipart）**：Minimal API 里用 `IFormFile` 参数绑定会走
> `[FromForm]` 的绑定路径，新版 ASP.NET Core 对它会要求 antiforgery。用手动读取即可绕开：
> `var form = await request.ReadFormAsync(ct); var file = form.Files["file"];` —— 不引入 `UseAntiforgery`，
> 与本项目"本地回环、单用户"的基线防护（设计文档 §10.4）一致。

**为什么生成要异步返回**：图像生成实测常在 10–60 秒，而本项目所有长动作都是"HTTP 立即回、结果走 SSE"
（会议开局、叙事开场都如此）。帧内不做长轮询，避免拖垮那条唯一 SSE 的读者语义。

## 五、SSE 事件（仍然只有一条流）

新增四个事件名，`js/stream.js` 里各加一个归约：

| 事件 | 载荷 | 时机 |
| --- | --- | --- |
| `image.job` | `{ jobId, status: "queued"\|"running", prompt, model, referenceIds }` | 收到 generate 请求后立刻 |
| `image.generated` | `{ jobId, images: [ImageAsset…], cost }` | 全部成功（含 `n>1`） |
| `image.failed` | `{ jobId, code, message }` | 失败（含 HTTP 非 2xx 的 `message`） |
| `image.list` | `{ images: [ImageAsset…] }` | SSE 首连与资产变化后的全量快照（与 `meeting.state` / `roleplay.state` 同款校准语义） |

`ImageAsset` 的 wire 形态与 `MaterialCard` 的 `Payload(...)` 一样是**手写投影**（`ImageProjection`），
避免把领域字段直接漏给前端。

> 新增事件必须**同时登记进设计文档 §8.3 的事件表**，并与 `wwwroot/js/stream.js` 的类型列表逐一对齐 ——
> 事件表是前后端唯一的契约（进度文档「风险 6」）。

## 六、provider 适配：OpenRouter `/api/v1/images`

### 为什么不用 SDK 的 `ImageClient`

`OpenAI` 2.13.0 里确实有 `OpenAIClient.GetImageClient(model)`，但它固定打 OpenAI 的
`/v1/images/generations`；而 **OpenRouter 的专属图像端点是 `{base_url}/images`**
（→ `https://openrouter.ai/api/v1/images`），且**响应形状不同**（`data[].b64_json` + `media_type`，
没有 hosted URL）。所以本模块**自己发 HTTP**（`IImageGenerator` + 一个实现），
这也符合项目"手写、可控、不加装饰器"的风格。

### 请求

```
POST {images.baseUrl}{images.endpointPath}        # 默认 https://openrouter.ai/api/v1 + /images
Authorization: Bearer <images.apiKeyEnv 指向的环境变量的值>
Content-Type: application/json
```

```jsonc
{
  "model": "google/gemini-3-pro-image",   // 或任意 image-capable slug
  "prompt": "…",
  "input_references": [                    // 参考图（可空）→ 图生图
    { "type": "image_url", "image_url": { "url": "data:image/png;base64,…" } }
  ],
  "n": 1,
  "aspect_ratio": "1:1",
  "resolution": "1K",
  "quality": "high",
  "output_format": "png",
  "seed": null
}
```

要点：

- 参考图**以 data URL 内联**（`data:image/png;base64,…`），不让服务端去访问本机 URL ——
  本机 URL 对 OpenRouter 不可达，且会引出新的暴露面。
- `endpointPath` 可覆盖：以后接 OpenAI 官方或其它兼容端点时写 `/images/generations` 即可。
- 单图 provider 会拒绝 `n > 1`，`maxCount` 默认设 1，界面把 `n` 收在 `1..maxCount`。

### 响应

```jsonc
{ "data": [ { "b64_json": "iVBORw0KGgo…", "media_type": "image/png" } ],
  "usage": { "cost": 0.0123 } }
```

实现必须处理的三个真实坑：

1. **`data` 是数组** —— 遍历，不要硬取 `[0]`；
2. **`media_type` 可能缺失**（例如返回 JPEG 却不带该字段）→ 用 **magic bytes 嗅探**兜底
   （`ImageBytes`：PNG `89 50 4E 47`、JPEG `FF D8 FF`、WebP `RIFF….WEBP`、SVG 以 `<?xml`/`<svg` 开头）；
3. **扩展名按嗅探结果取**，不能一律写 `.png`。

非 2xx 时把响应体前若干字符带进 `image.failed.message`（截断到 300 字符，同 `fetchModels` 的做法），
让"模型不对 / 参数不支持 / 余额不足"这几类错误一眼可辨。

## 七、网络与代理（Windows / PAC）——本模块唯一的实测风险

用户的出网依赖 Windows 上的 PAC（`AutoConfigURL`），而 MeetingRoom 目前**没有任何代理配置**。
好消息是 .NET 侧默认就会用上它：

- `HttpClient.DefaultProxy` 在 **Windows 上先读环境变量**（`HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` / `NO_PROXY`），
  只有它们未设置时才**回退到当前用户的 WinINET/IE 设置**；
- 内部实现 `HttpWindowsProxy` 在 `AutoSettingsUsed`（勾了"自动检测设置"或填了自动配置脚本）时
  会调用 **WinHTTP 去下载并执行 PAC 脚本**，并按目标 URL 求值；
- .NET 9+ 起还会**监听 Internet Settings 注册表变化并自动刷新**代理（.NET 10 同样；
  打包/UWP 应用受注册表虚拟化影响，本项目的自包含 exe 不受影响）。

结论：**默认零配置就能走用户设的 PAC**，前提是进程环境里没有 `HTTP_PROXY` 之类（已验证为空）。
但仍要按"先实测、再定型"办，所以：

1. 批 A 第一步加一个 `--probe-image "<prompt>"` 自检入口（照 `--probe-chat` 的写法，
   输出 HTTP 状态、字节数、嗅探到的 media_type，**不打印密钥、不打印完整 base64**）；
2. 配置留逃生口：`images.proxy = ""`（默认，用系统代理）/ `"off"`（直连）/ `"http://127.0.0.1:10828"`（显式）。
   非空时用 `SocketsHttpHandler.Proxy = new WebProxy(...)` + `UseProxy = true`；
   `"off"` 时 `UseProxy = false`。

> 注：.NET 的 `HttpClient` **不读** WinHTTP 的机器级配置（`netsh winhttp show proxy`），
> 只读环境变量与 WinINET —— 上一轮已确认用户机器的 WinHTTP 是"直接访问"，所以此处不受影响。

```jsonc
  "images": {
    "enabled": true,
    "baseUrl": "https://openrouter.ai/api/v1",
    "endpointPath": "/images",              // OpenAI 官方端点写 /images/generations
    "model": "google/gemini-3-pro-image",
    "apiKeyEnv": "OPENROUTER_API_KEY",      // 只存变量名；值放 <Reasonix home>/.env 或进程环境
    "timeoutSeconds": 120,                  // 0 = 不设客户端超时（仍受取消控制）
    "proxy": "",                            // "" = 系统代理；off = 直连；或 "http://127.0.0.1:10828"
    "maxReferenceImages": 3,
    "maxReferenceBytes": 8388608,           // 8 MiB/张
    "maxOutputBytes": 16777216,             // 16 MiB/张
    "defaultAspectRatio": "1:1",
    "defaultResolution": "1K",
    "defaultQuality": "auto",
    "outputFormat": "png",
    "maxCount": 1,                          // n 的上限
    "keepReferences": true                  // 导入的参考图是否留在 images/refs/
  }
}
```

`ConfigLoader.Validate` 里加校验（**非法值拒绝启动并说明原因**，不静默回退）：

| 规则 | 违反时 |
| --- | --- |
| `baseUrl` 必须是绝对 `http(s)` URL | `images.baseUrl 必须是 http(s) 绝对地址：…` |
| `endpointPath` 必须 `null` 或 `/` 开头 | `images.endpointPath 必须以 / 开头：…` |
| `model` 非空（`enabled = true` 时） | `images.model 不能为空：图片生成需要 image-capable 模型 slug。` |
| `apiKeyEnv` 非空 | 同上句式 |
| `timeoutSeconds ≥ 0`、`maxCount ∈ 1..10`、体积上限 `> 0` | 逐项给出当前值 |
| `proxy` 只接受 `""` / `off` / 绝对 URL | `images.proxy 只接受空、off 或绝对 URL：…` |

`GET /api/config`（诊断端点）也要把 `images` 节吐出来（密钥只露变量名），
并在启动诊断里加一行 `图片生成：{baseUrl}{endpointPath} 模型 {model}（key 变量 {apiKeyEnv}）`。

**密钥怎么进进程（会踩的那个坑）**：`images.apiKeyEnv` 指的环境变量必须**在进程启动时就存在** ——
这与 `DEEPSEEK_API_KEY` 是同一条既有教训（进度文档「风险 2」：用户级环境变量在宿主**已启动之后**才写入时，
子进程继承不到，表现为"环境变量未设置"）。做法二选一：`setx OPENROUTER_API_KEY …` 之后重启宿主；
或从终端把那一个变量注入进程再 `dotnet run`。本模块**不做 `.env` 读取** ——
`.env` 是 Reasonix 的机制，MeetingRoom 只认进程环境（`OpenAiCompatibleModelFactory` 已经是这个规则）。

**客户端预检**（发请求之前做，省一次白传）：
- `file.type.startsWith('image/')`，否则提示"只能选图片"；
- `file.size <= images.maxReferenceBytes` —— **从 `GET /api/config` 的 `images` 节读**，不在前端写死（避免两处数字不一致）；
- 已选张数 + 本次 ≤ `images.maxReferenceImages`。

任一不通过就地把卡片标红并说明原因，**不发请求**（验收里专门盯这一条）。

**上传中的表现**：卡片先以 `data-state="uploading"` 出现（文件名 + "上传中…"）。
**上传进度条明确不做**（2026-10 决定）—— `fetch` 没有上传进度事件，要做就得上 `XMLHttpRequest`；
本模块不引入，也不列为后续可选项。

**去重是幂等的**：同一张图拖两次，第二次返回 `{ reused: true, asset }`，界面提示"这张已导入（复用 img-0003）"，
网格里**不出现第二张**。

### 生成结果的显示

1. **提交即占位**：`POST /api/images/generate` 返回 `{ jobId }`、同时收到 `image.job` → 在 `#studio-results` 里插一张
   `data-state="running"` 的占位卡，**带已过去秒数的计时**。30–60 秒是常态，没有计时看起来就像卡死 ——
   与本项目「等待答复必须有提示」（顶栏 pill）是同一条教训。
2. **成功**：`image.generated` 到达 → 按 `jobId` 把占位卡换成真实资产卡；`n > 1` 时展开成多张。
   卡片信息：缩略图 + prompt 摘要（悬停看全）+ `model` + 体积 + `cost`。
3. **失败**：`image.failed` → 占位卡变 `data-state="error"`，把 `message` **原样显示且可选中复制**，并提供「重试」
   （带上原参数）。这样"模型 slug 不对 / 参数不被支持 / 余额不足"三类上游错误一眼可辨。
4. **放大**：点缩略图 → `#image-viewer` 显示原图（`<img src="…/content?v=<sha256 前 8 位>">`）。
5. **操作**：另存为…（`POST /api/images/{id}/save-as` → 原生另存对话框）、复制提示词（`navigator.clipboard`）、
   删除（二次确认；删文件 + manifest 条目）。
6. **刷新后仍在**：靠 `image.list` **全量快照**恢复，**不要**依赖增量事件 —— 需要重建的东西就必须进快照
   （与进度文档「风险 13：重连快照不含讨论区消息」是同一条方向）。
7. **关掉浮层不打断生成**：生成在服务端跑、事件照收；重新打开浮层就能看到结果（事件不依赖浮层开着）。

### 渲染约束（两条必须落到实现里）

1. **不要每次 `render` 重建 `<img>` 节点**。按 `asset.Id` 维护一个 `Map<id, HTMLElement>`，只做"增 / 删 / 改字段"。
   否则帧批渲染每帧换掉 `<img>` → 浏览器重新解码与绘制，表现为**图片一闪一闪、滚动位置跳动**。
2. **`src` 只在内容变化时才变**：`?v=<sha256 前 8 位>` 作缓存键，同一张图在两次 render 之后的 `src` 必须完全相同
   （验收里用 `evaluate` 断言这一条）。

### 键盘与空态

- `Esc` 关闭浮层（照 `viewer.js` 既有的做法）；`Ctrl+Enter` 在提示词框里提交生成。
- `#studio-refs` 空态：`还没有参考图 —— 拖一张进来，或点「选图片…」（纯文生图也可以直接生成）`。
- `#studio-results` 空态：`还没有生成过。`
- 没有工作空间 / 未配置 key：入口按钮 `disabled` + `title` 说明原因（与"开始会议"按钮的既有禁用逻辑一致）。

### 批 D：MCP 接入（**已落地**，2026-10）

比前端更早落地的一条路：把生成内核包成 **stdio MCP 服务**，由宿主（Reasonix）直接调用。

| 落点 | 内容 |
| --- | --- |
| 独立的 MCP 服务（不在本仓库） | `ModelContextProtocol` + stdio 传输；**只回路径、不回图片内容块**（一张图进上下文很贵） |
| 复用什么 | **零拷贝**：`OpenRouterImageGenerator` / `ImageSource` / `ImageBytes` / `ImageHttp` / `ImageOptions` 全部来自 `MeetingRoom.Core`；MCP 只做"读配置 + 落盘 + 工具面"三件事 |
| 三个工具 | `generate_image`（prompt + `referencePaths` + model/resolution/aspectRatio/outDir）/ `list_image_models` / `image_gen_status` |
| 失败语义 | 一律转 `{ ok: false, error: "…" }` 的 JSON 而**不抛异常** —— 抛进 MCP 协议层只会变成一句笼统错误，而上游原话（slug 不对 / 参数不被支持 / 余额不足）才是最该看到的 |
| 配置 | `--config <meetingroom.json>` **只读**其 `images` 节（绝不写文件）→ 命令行覆盖 → 内置默认；密钥只从进程环境读 |
| 薄 skill | 宿主 skills 目录下的 `image-gen/SKILL.md`（工具名 + 已知档位表 + 命令行兜底） |
| 实测（2026-10） | `dotnet build` 0 警告 0 错误；`--selftest` 图生图出图（JPEG 282 KB / 17.1 s）；`initialize` + `tools/list` 验得 `serverInfo: ImageGenMCP` 与三个工具已注册 |

**为什么这条比前端更合适**：这种用法本质是"一次调用换一张图" —— 没有会话状态、没有多轮、没有实时协作，
正好是 MCP 工具的形状；而独立窗口要维护浮层、三条上传通道、SSE 归约与图片网格，成本高出一个量级。
生成内核完全共用，所以**哪条入口都不影响另一边**（这正是抽象分层想要的）。

## 十二、风险与未决项

| 风险 | 说明与应对 |
| --- | --- |
| **PAC 出口未实测**（首要） | .NET 支持 PAC 是文档与源码事实，但"这台机器上是否真的走通"必须用 `--probe-image` 验；失败则用 `images.proxy` 显式指向 `http://127.0.0.1:10828` |
| 请求体膨胀 | 参考图以 base64 内联（约 +33%）→ `maxReferenceImages` / `maxReferenceBytes` 双上限，超限在 `POST /api/images/reference` 就拒绝 |
| 长耗时 | 30–60s 是常态 → 异步 + SSE + `timeoutSeconds`；**不**在前端做轮询 |
| 模型 slug 不存在 | 上游返回 404/400 → 原样带进 `image.failed.message`；界面提供"从 `/api/v1/images/models` 拉一次可选模型"作为后续增强（本轮不做） |
| 前端无自动化测试（项目惯例） | 靠 MCP 真机 + 结构化断言兜着（与本项目既有做法一致） |
| `--probe-chat` 之类临时入口的清理 | `--probe-image` 若批 C 后仍要留作诊断，则**明确写进进度文档**，不要变成"忘了删的临时物"（阶段 2 的 `--probe-chat` 就是前车之鉴） |

**用户未答的两问，本方案采用的默认值**（都只需一处改动即可切换）：

| 问题 | 采用的默认 | 想改时动哪里 |
| --- | --- | --- |
| 参考图用途 | 当前只作为**图生图的参考**（不喂给角色 Agent）——与"图片识别能力留后续"一致 | 后续那批在 `ContextComposer` 里加附件即可 |
| 资产归属 | **工作空间级** `images/`（参考图与结果同层） | `WorkspaceLayout.ImagesDir` → 改成会话目录 |

## 十三、与"角色卡图片识别"的衔接（下一批，本轮只预留）

本批刻意留下的三个接口，让下一批不必返工：

1. **资产 id 稳定且带元信息**：`img-0001` + `manifest.json` 里的 prompt / model / sha256，
   下一批要把哪张图喂给哪个角色，有据可查；
2. **角色卡 frontmatter 预留字段**：`images = ["img-0001"]`（本轮**不解析、不校验**，
   只在文档里登记该约定，避免与"角色卡格式约束"（设计方案 §5.4）冲突）。
   选**数组写法**而不是嵌套结构，是因为 `RoleCardLoader` 只支持 `key: value` 与 `key: [a, b]`
   两种形态（进度文档「风险 10」）——`images = ["img-0001"]` 正好落在受支持的那一侧，
   下一批做图片识别时不必先扩解析器；
3. **图片进模型 = `DataContent`**：将来在 `ContextComposer.Compose` 的**私有段**（角色卡节之后、
   私有历史之前）注入附件，就能做到"只有这个角色看得到这张图"，
   而共享前缀（system + 会议公共节）**仍然字节稳定**（硬约束 6）。

## 十四、后续方向：多 Agent 图片工作流（2026-10 提出）

用户的判断是：**图片生成这类"一对一"调用不需要自己的前端**；它的价值要在"多 Agent 协作"里才真正展开 ——
而 MeetingRoom 的核心能力（多角色会话、编排、资料/资产、可见性、节奏控制）恰好就是这个形状。
所以本模块**保留全部后端接口**，作为将来这条线的地基：

| 已有的地基 | 在多 Agent 工作流里的可能角色 |
| --- | --- |
| `ImageEndpoints` 的 6 个端点 + `image.*` 事件 + `image.list` 快照 | 让图片工作流跑在**同一套 SSE 与状态快照**上，不必另造实时通道 |
| `ImageAssetStore`（`refs/` + `out/` + manifest） | 参考图与产出的**资产层**，可被角色卡引用（§十三 的 `images = ["img-0001"]`） |
| `ImageStudio`（按当前工作空间取库 + 后台任务） | 与 `SessionHub` 同层的组合根：多 Agent 场景下它管"谁在生成什么" |
| `Core/Orchestration/*`（`SessionCore` / 策略 / 打断 / 待决机制） | 多个"图片 Agent"（出题 / 生成 / 评审 / 挑选）之间的调度、打断与人工拍板 |
| MCP 接入（批 D） | 外部宿主（Reasonix）参与**同一批资产**，而不是另开一条平行路径 |

**注意**：这是**方向声明，不是本轮实现范围**。真要落地得先回答三个问题：
① 图片 Agent 的产出怎么进上下文（回到 §十三 的 `DataContent` 那条路）；
② 参考图 / 产出的可见性是否按角色裁剪（用既有 `Visibility.VisibleTo`）；
③ 要不要"图片评审"环节（复用资料库的六级状态机，还是另立一套）。

## 附：一句话总结

图片生成模块 = **一个 `HttpClient` + 一份资产库 + 两种入口**（MCP 工具 / 命令行）；
它复用了项目已有的五件基础设施（事件总线、配置校验、系统对话框、路径防护、原子落盘），
不进入编排内核、不进上下文、不加工具面 —— 所以现有功能**一行行为都不变**。

入口这件事有两个决定值得记住：

- **不需要自己的前端**（用户 2026-10）：一次调用换一张图的用法，MCP 工具就是它的形状（批 D 已落地）；
- **后端接口全部保留**：它们是"多 Agent 图片工作流"（§十四）的地基，撤掉反而要重造。

唯一需要实测的外部变量是网络出口（Windows PAC 与 .NET 的交互）—— `--probe-image` / `--selftest`
已在真机上验过：**系统 PAC 会被 .NET 默认采纳**，零配置即可出网。
