# 战斗托管设计（MeetingRoom × 5E 2024）

> 前置：V3 单次判定版已落地（`Sheet` / `D20` / `WeaponMasteries` / `RulesData`），
> 真实规则包已由 `--probe-rules` 实测反序列化通过。
> 本文设计**战斗托管**（谁先动、每回合能做什么、数值怎么变、何时结束）与**叙事检定**
> （游说/洞悉/察觉/巧手这类不改变 HP、但改变“谁知道什么、局面往哪走”的判定）。
> 不在本文范围：AI 提示词改法、前端具体样式、模组素材。

---

## 1. 目标与非目标

**目标**

- 引擎持有战斗的**权威状态**（先攻、回合、行动经济、HP、状态），AI 只提议、不裁决。
- 叙事检定同样走引擎：**谁发起、DC 多少、结果是否采纳**三者分离，DM 掌握难度与最终裁量。
- 用户（导演/DM）随时能否决或直接改数，所有改动留痕。
- 每一步都能落进 `story.jsonl` 并重放出同一个结果（与 `kind=roll` 同规则）。
- 与枭熊地图联动只做**只读**：距离/射程来自 `VttContext`，引擎不写回 OBR。

**非目标（本版不做）**

- 自动寻路与多格体型；飞行高度；掩体的几何判定（只接受 DM 给的掩体等级）。
- 自动战斗 AI（敌人由 DM 或说书人按剧本演，不由引擎推演最优解）。
- 与 OBR 的双向同步（移动 token 写回留给 V4）。

## 2. 分层

```
┌────────────────────────────────────────────────────────────────┐
│ 叙事层（说书人 + 角色 Agent）                                    │
│   · 角色 Agent：人物想做什么（意图：我想游说守卫）               │
│   · 说书人：把意图翻成 CombatIntent / CheckRequest，叙述结果     │
└───────────────┬────────────────────────────────────────────────┘
                │ ITableActions（只提议）
┌───────────────▼────────────────────────────────────────────────┐
│ 托管层（CombatEngine + CheckEngine，新增）                       │
│   · Encounter 状态机：先攻 → 回合 → 结束                         │
│   · CheckRequest 裁决：技能/属性/对抗/被动                       │
│   · 合法性校验：动作经济 / 射程 / 资源 / 状态限制                │
│   · 调用 V3 判定器（D20 + Sheet + RulesData）                    │
│   · 产出 CombatEvent / CheckEvent（结构化，可重放）              │
└───────┬───────────────────────────────┬────────────────────────┘
        │ 只读                             │ 落盘
┌───────▼──────────┐          ┌─────────▼────────────────────────┐
│ 地图层 VttContext │          │ StoryTimeline                    │
│  距离 / 网格       │          │  combat-* / check 记录           │
└──────────────────┘          └──────────────────────────────────┘
```

关键原则：**叙事层永远拿不到“改数”的接口**。说书人只能 `SubmitIntent` / `RequestCheck`，引擎返回事件或拒绝；DM 的改数走 `DmOverride` 并带审计字段。

## 3. 领域模型

```csharp
Encounter {
  Id, Round, Seed,                    // Seed 进事件，保证重放
  Phase: Setup | Initiative | Active | Ended,
  Combatants: Combatant[],
  Order: string[],                    // 按先攻排序的 combatantId
  CurrentIndex,
  Turn: TurnState?,
  Outcome?: Victory | Defeat | Retreat | DmEnded,
  StartedAtSeq, EndedAtSeq
}

Combatant {
  Id, DisplayName, CnName,
  Side: Party | Foe | Neutral,
  SheetId?, TemplateId?,
  Initiative, InitiativeTiebreak,     // 平手：DEX → 实体 id
  ControlledBy: Ai | Dm,
  VttTokenId?
}

TurnState {
  ActorId,
  ActionUsed, BonusUsed, ReactionUsed: bool,
  MovementUsedFeet, MovementMaxFeet,
  EndedBy?: Dm | Engine
}
```

叙事检定不进入 `Encounter`，它有自己的请求模型：

```csharp
CheckRequest {
  Id,
  ActorId,
  Kind: Ability | Skill | Contest | Passive,
  Skill?, Ability,                    // Skill 时 Ability 由技能表推导（如 Athletics→str）
  DC,                                 // 由 DM 给；说书人可提议，但记 DcSource
  DcSource: Dm | Narrator | RulesTable,
  Advantage: Normal | Advantage | Disadvantage,
  Reason,                             // 为什么要检定（进日志与正文）
  Visibility: Public | Secret,        // Secret = 暗骰，角色 Agent 看不到数值
  Stakes?: { OnSuccess, OnFailure, OnPartial },   // 后果，供叙述
  OpposedBy?: { ActorId, Skill }      // 对抗检定（Contest）
}

CheckResult {
  CheckId, Success, Critical, Fumble,
  Natural, Modifier, Total,
  Visibility, Applied: bool           // DM 可否决采纳
}
```

`Sheet` 仍是唯一数值真相；`Combatant` 与 `CheckRequest` 都只是视图/请求，不缓存 HP。

## 4. 状态机与回合生命周期

```
Setup ──start_combat──▶ Initiative ──roll_initiative(或 DM 直填)──▶ Active
                                                                    │
                    ┌───────────────────────────────────────────────┤
                    ▼                                               │
             BeginTurn(actor)                                       │
                    │                                               │
         ┌──────────┴──────────┐                                    │
         │ AI/DM 提议 intent    │                                    │
         │ 引擎校验 → 掷骰 → 应用│                                    │
         └──────────┬──────────┘                                    │
                    ▼                                               │
             EndTurn(actor) ── 还有可行动者 ──▶ BeginTurn(下一人)    │
                    │                                               │
                    └── 一方全倒 / DM 宣布 ──▶ Ended ───────────────┘
```

回合内顺序（引擎强制）：

1. `BeginTurn`：重置 action/bonus/reaction/移动；处理“回合开始”触发（持续伤害、再生、状态到期）。
2. 接受 0..N 次 `SubmitIntent`，每次立即校验并结算（不批量暂存，避免 AI 攒一堆非法动作）。
3. `EndTurn`：处理“回合结束”触发（豁免结束、专注检定等），推进到下一个可行动者。
4. 跳过规则：`Incapacitated` / `Unconscious` 自动 `BeginTurn → EndTurn`，不消耗输入机会。

一轮（Round）在 `CurrentIndex` 回到 0 时 +1；回合数只在 `BeginTurn` 加。

**叙事检定不参与上述状态机**：它没有回合、没有行动经济，可以在任何时刻发起（包括战斗中，此时是否消耗 Action 由 DM 判定）。

## 5. 动作分类与校验

| 动作 | 消耗 | 引擎校验 | 结算 |
| --- | --- | --- | --- |
| `Attack`（武器/法术攻击） | Action（或 Bonus，如双持） | 射程（reach/range vs `VttContext`）、目标可见、武器已装备 | `RollAttack` → 命中则 `RollDamage`（含精通） |
| `CastSpell` | 按 `spells.time` | 法术位/已知、施法距离、目标合法性 | 攻击型 `RollAttack`；豁免型 `RollSave`；治疗走 `RollDamage` 变体 |
| `Move` | 移动尺数 | 剩余移动 ≥ 距离；困难地形由 DM 声明倍率 | 更新位置（仅记录，不写回 OBR） |
| `Dash` | Action | — | 本轮移动 +速度 |
| `Dodge` | Action | — | 标记 `Dodging`（攻击对其有劣势），持续到下一回合开始 |
| `Disengage` | Bonus（2024） | — | 标记 `Disengaged`（不引发借机攻击） |
| `Hide` | Action | 需 DM 给掩护条件 | 标记 `Hidden`（DM 可随时撤销） |
| `Help` | Action | 目标在 5 尺内 | 给目标下一次检定优势（一次性） |
| `Ready` | Action | — | 存触发条件，DM 判定触发 |
| `UseObject` | Action/Bonus | 物品存在（`rules-data.items`） | 药水：Bonus Action（2024） |
| `SkillCheck`（战斗内） | 通常 Action（DM 可判为 free） | 同 §6 | 走 `RequestCheck`，不直接改 HP |
| `Custom` | 由 DM 指定 | 不校验 | 记录描述，数值由 DM 覆盖 |

共同前置：**行动者存活且非 `Incapacitated`**；反应只能在当前回合之外触发，每轮一次。

## 6. 叙事检定（非战斗判定）

### 6.1 定位

战斗检定改变 HP，叙事检定改变**信息与局面**：游说是否说服、洞悉是否看穿、察觉是否注意到、巧手是否得手。它同样用 d20，但有独立的请求与裁决路径。

### 6.2 发起与裁决分离

| 环节 | 谁能做 | 规则 |
| --- | --- | --- |
| **发起** | 任何角色 Agent、说书人、DM | 角色说“我想游说守卫” → 说书人翻成 `CheckRequest`；DM 也可直接要求“做个察觉” |
| **定 DC** | DM（最终）；说书人可提议 | 记为 `DcSource`：`dm` / `narrator` / `rulesTable`。说书人不能既定 DC 又立刻宣称成功 |
| **裁决** | 引擎（掷骰）+ DM（采纳/否决） | DM 觉得“这人根本不可能被说服”可以 `Applied=false`，事件仍留痕 |
| **叙述** | 说书人 | 只能叙述已采纳的结果；`Secret` 暗骰不得报数值 |

### 6.3 四种形态

| 形态 | 例子 | 结算 |
| --- | --- | --- |
| 属性检定 | 力量推门、体质硬撑 | d20 + 属性调整值 |
| 技能检定 | 游说 / 洞悉 / 察觉 / 巧手 / 隐匿 / 调查 | d20 + 属性 + 熟练（有专精则双倍） |
| 对抗检定 | 隐匿 vs 被动察觉；巧手 vs 察觉 | 双方各掷取总值比较，平手按“防守方胜” |
| 被动值 | 被动察觉 = 10 + 加值 | 不掷骰，直接与 DC/对抗值比较 |

2024 群体检定（全队潜行）：按“半数成功即通过”处理，由 DM 决定是否用群体规则。

### 6.4 暗骰（Secret）

- 结果只进 DM 视角与事件日志；**角色 Agent 的上下文里只有“你不知道他有没有相信你”**。
- 说书人可见结果（它要写反应），但提示词禁止报出数值或“你失败了”。
- DM 可随时把暗骰转公开（`DmOverride` 改 `Visibility`）。

暗骰是 V1 `visible` 同思路的信息闸门：**不是靠提示词“请勿剧透”，而是机制上不给**。

### 6.5 难度口径

DM 定 DC，参考规则表（Very Easy 5 / Easy 10 / Medium 15 / Hard 20 / Very Hard 25 / Nearly Impossible 30）。说书人可提议 DC，但必须带 `DcSource`；连续同一理由的重复检定要**递增难度或直接拒绝**（见 §6.6）。

### 6.6 防滥用

- **同一目标同一理由**：记录（actor, target, skill），第二次起 DC +5 或直接“你已经试过，他不吃这套”。避免无限刷游说。
- **失败要有后果**：`Stakes` 里写清 `OnFailure`（叫增援、态度恶化、时间流逝）；没有后果的检定不做。
- **限制发起密度**：非战斗场景下，一次导演指令最多触发 2 次检定（说书人自行发起的），超出需 DM 确认。
- **检定不该替代扮演**：玩家描述得好（有具体理由、抓住把柄）→ DM 可给优势或直接成功；这是 DM 裁量，引擎只记录。

### 6.7 与地图的联动

- 察觉看隐藏目标：依赖 `VttContext` 的 `visible` 过滤——未揭示的 token 连“有东西”都不该知道，除非检定成功。
- 潜行/追逐：距离来自 `VttContext`；DM 可据此调 DC（远处更容易藏）。
- 缺地图时降级：DM 口述距离与掩体，检定照常。

### 6.8 事件契约

```jsonc
{"kind":"check","checkId":"chk-1","actor":"ella","kindType":"skill",
 "skill":"persuasion","ability":"cha","dc":15,"dcSource":"dm",
 "roll":{"natural":12,"modifier":5,"total":17,"success":true},
 "visibility":"public","reason":"说服守卫放行",
 "stakes":{"onSuccess":"放行","onFailure":"叫增援"}}

{"kind":"check","checkId":"chk-2","actor":"ella","kindType":"skill",
 "skill":"insight","dc":14,"dcSource":"narrator",
 "roll":{"natural":3,"modifier":2,"total":5,"success":false},
 "visibility":"secret","reason":"看穿商人是否在撒谎",
 "stakes":{"onSuccess":"识破谎话","onFailure":"你相信了他的说法"}}

{"kind":"check-override","checkId":"chk-2","applied":false,
 "reason":"DM 认为此人无论如何不会露馅"}
```

## 7. 与现有代码的接点

| 现有 | 用法 |
| --- | --- |
| `Sheet` / `SheetValidator` | 数值来源；检定前校验属性/熟练完整 |
| `D20.RollCheck` | 叙事检定的唯一入口（技能/属性/对抗/被动都走它） |
| `D20.RollAttack/RollSave/RollDamage` | 战斗结算；与叙事检定共用随机源 |
| `WeaponMasteries` | 攻击结算按 `items.mastery`；**未建模的照常结算**，但在回执与事件里显式标注「本次未生效」——不静默、也不因此禁掉这把武器 |
| `RulesData` | 查法术、物品、动作；**技能表**（`skills` 段，18 项与属性映射） |
| `VttContext` | 距离/可见性；察觉与潜行的输入 |
| `ITableActions` | 新增 `StartCombat/SubmitIntent/EndTurn/EndCombat/RequestCheck/DmOverride` |
| `StoryTimeline` | 新增 `combat-*` 与 `check`；重放不推 revision |
| `NarratorToolDispatcher` | 新增 `start_combat` / `combat_action` / `next_turn` / `end_combat` / `request_check` |
| `RoleplayStrategy` | **不改**；检定不改变选角与披露逻辑 |

## 8. 事件与落盘契约（战斗）

```jsonc
{"kind":"combat-start","encounterId":"enc-1","round":1,"seed":12345,
 "order":[{"actor":"ella","initiative":18,"dexterityModifier":3,"tiebreak":"dex"},
          {"actor":"goblin-1","initiative":12,"dexterityModifier":2,"tiebreak":""}],
 "combatants":[{"id":"ella","displayName":"Ella","side":"party","initiative":18,
                "dexterityModifier":3,"speedFeet":30,"controlledBy":"ai"}]}

{"kind":"combat-turn","encounterId":"enc-1","round":1,"actor":"ella",
 "budget":{"action":true,"bonus":true,"reaction":true,"movementFeet":30}}

{"kind":"combat-action","encounterId":"enc-1","actor":"ella","action":"attack",
 "target":"goblin-1",
 "roll":{"natural":14,"modifier":5,"total":19,"targetAc":15,"success":true,"crit":false},
 "damage":{"parts":[{"dice":"1d8+3","type":"slashing"}],"applied":6,"hpAfter":1},
 "distanceFeet":10,"mastery":"Sap"}

{"kind":"combat-action","encounterId":"enc-1","actor":"ella","action":"attack",
 "rejected":{"code":"out-of-range","message":"目标在 60 尺外，弯刀只能打到 5 尺"}}

{"kind":"combat-end","encounterId":"enc-1","outcome":"victory","rounds":4}
```

约定：

- 事件里**必须有 `rejected` 分支**：AI 提议被拒也是正史，要能叙述“你够不到他”。
- 伤害事件记录分桶明细与 `hpAfter`；`seed` 必进 `combat-start`。
- `combat-start` **必须带完整 `combatants`**（不只是 order）：重放时要靠它重建参战者与敏捷调整值，
  否则换台机器/换进程就还原不出同一顺序。
- `encounterId` 用单调递增 `enc-N`，与 `story.jsonl` 的 turn 序号解耦。
- 落盘形状沿用 V2/V3 的约定：`{kind, "<kind>": record}`（record 里带 `at`），
  与 `roll` / `check` / `attack` / `damage` 完全同构，读回时按同一个 key 取。

## 9. DM 覆盖与异常路径

| 场景 | 处理 |
| --- | --- |
| DM 改数（加血、临时 HP、判死） | `DmOverride { target, field, value, reason }` → 写 `combat-override` 事件 |
| DM 加怪/撤怪 | `DmAddCombatant` / `DmRemoveCombatant` |
| DM 改 DC 或否决检定 | `check-override` 事件；`Applied=false` 但留痕 |
| AI 提议非法动作 | `rejected` 事件，说书人必须叙述失败原因，不得重试绕过 |
| 数据包/VTT 不可用 | 降级：距离与射程由 DM 判断；引擎只保证行动经济与 HP |
| Sheet 缺字段 | `SheetValidator` 拒绝参战，提示缺项 |
| 同一 Sheet 重复参战 | 拒绝，要求先结束上一场或克隆 |

## 10. 分期与验收

| 期 | 内容 | 验收 |
| --- | --- | --- |
| **C1 骨架** ✅ 已落地（2026-10-26） | `Encounter` 状态机、先攻掷骰与平手、`BeginTurn/EndTurn`、`StartCombat/EndCombat`；数值暂手填 | 两人走完 3 轮；平手按 DEX→id；顺序可重放 |
| **C2 攻击 + 叙事检定** | `Attack`/`CastSpell` 接 `D20`+`RulesData`；`RequestCheck` 四种形态、暗骰、`Stakes`、防刷 | Vecna +13 与 Longsword `1d8+3` 与手算一致；游说/洞悉/察觉/巧手各一例；暗骰不泄漏数值 |
| **C3 行动经济与移动** | action/bonus/reaction、移动尺数、Dash/Dodge/Disengage/Hide/Help；`VttContext` 距离 | 一回合两次 Action 被拒；超速被拒；5/30 尺判定正确 |
| **C4 反应与持续效果** | 借机攻击、Ready、专注检定、状态到期 | 借机攻击只触发一次；专注被打断有豁免事件 |
| **D1 死亡豁免**（设计 §18） | `VitalStatus` 四态、死亡豁免、稳定、治疗与 massive 衔接 | 濒死→稳定 / 濒死→死亡两条路径可重放；回合开始顺序固定 |
| **D2 法术位**（设计 §19） | `SpellSlots` 校验、升环伤害、长休恢复 | 戏法不耗槽；无槽/环级不足被拒；升环伤害正确 |
| **D3 DmOverride**（设计 §20） | 白名单字段、`combat-override` 事件、可重放 | 改 HP 触发状态迁移；override 可从日志重放 |

## 11. 测试策略

- **纯函数/状态机单测**：先攻平手、行动经济、射程拒绝、伤害分桶、回合推进、技能加值推导、被动值。
- **叙事检定单测**：四种形态各一例；暗骰结果不进角色上下文；重复检定递增 DC；`Applied=false` 不改状态。
- **`--probe-combat`**：脚本化遭遇 + 一段叙事检定，打印事件流与最终 HP。
- **BrowserDebug 端到端**：起 Host → 建叙事会话 → 触发战斗与检定 → `evaluate` 断言第 5 列的先攻序/HP 与检定的可见文案。
- **重放测试**：同一 `story.jsonl` 重放两次，`Encounter` 与 `CheckResult` 快照逐字段一致。

## 12. 风险

1. **AI 提议质量**：模型常给“射程外攻击”“一回合两次动作”。引擎硬拒，且回执要能让说书人叙述出原因。
2. **数值双写**：`Sheet` 是唯一真相，`Combatant`/`CheckRequest` 不缓存 HP。
3. **重放一致性**：先攻、伤害、检定都依赖随机源；seed 必须进事件。
4. **规则边界蔓延**：反应、传奇动作、多轮状态最容易写成半个 VTT；C4 之前只记录 + DM 判定。
5. **叙事节奏冲突**：允许 `Custom` 与 `DmOverride` 打破僵局，不能因为校验卡住剧情。
6. **检定泛滥**：每句话都检定会让跑团变成掷骰流水线。用 §6.6 的密度限制与“无后果不检定”兜住。
7. **暗骰泄露**：说书人知道结果却要装作不知道——提示词只能降低概率，机制上要靠“角色上下文不含数值”。

### 15.2 HP 规则（写进实现与测试）

1. **临时 HP 先吸收**，溢出的部分才扣当前 HP。
2. 当前 HP 掉到 0：**昏迷**（`Unconscious`），等死亡豁免结算（后续）。
3. 单次溢出伤害 ≥ 最大 HP：**直接死亡**（`Dead`）。这是 5e 2024《玩家手册》"立即死亡（Instant Death）"的简化：
   规则原文是"剩余伤害等于或超过生命值上限时立即死亡"，我们取同一阈值（≥ 最大 HP），不做后续死亡豁免。
4. `SetHp`（治疗 / DM 改数）把当前 HP 拉回正值时，状态复位为 `Alive`；已死亡的不自动复活。
5. 目标没有登记、或 HP 字段未填：**拒绝扣血并说明原因**（不静默）。
6. **死亡豁免未结算（明确未做）**：0 HP 只是 `Unconscious`，**不等于稳定**、也**不记**死亡豁免成功/失败；
   治疗 / 稳定 / 死亡三态的完整规则留给后续一期。不要因为看到 `Unconscious` 就以为豁免已经掷过了。

### 16.2 口径

   **同一轮对同一目标只触发一次**；移动者本回合 Disengage 过则不触发。
3. **Ready**：消耗 Action 存触发条件（`ReadyTrigger`），持续到自己的下一回合开始；触发执行由 DM 判定。
4. **专注**：受伤时 CON 豁免，`DC = max(10, 伤害/2)`；失败清 `Sheet.Concentration`，落 `kind=check`（`kindType=save`、`ability=con`、`focus=true`）。
5. **Help**：被帮助者的下一次攻击用优势后立刻清除（`ConsumeHelp`），不跨回合累积。
6. **状态到期**：`Combatant.ConditionRounds` 在自己的回合开始时递减，到 0 移除并记入 `Encounter.ExpiredConditions`。

### 17.5 显式边界：两个"不自动"（不是 bug）

C4 有两处**故意只做一半**，理由是设计 §9「DM 裁定」的分工，以及"自动掰下去反而更差"：

1. **借机攻击只判触发，不代打。**
   引擎负责判定：离开了谁的触及、对方的 reaction 本轮是否还没用、移动者是否 Disengage 过、
   同一轮对同一目标是否已经触发过。判定通过后它只做三件事——消耗那次 reaction、落一条
   `combat-action`（`action="opportunity-attack"`）、在回执里提示"谁可以对他做一次借机攻击"。
   **那一次攻击本身由 DM 用一次 `combat_action` 打出**（自己选武器、写加值与伤害）。
   引擎**不代选武器**：要自动选就得引入"用哪把武器 / 是否双持 / 是否用精通 / 是否改用徒手"一整套规则，
   而 DM 本来就可能在剧情上选一把更合适的武器——强行自动会把裁定权从 DM 手里拿走。
   所以看到"触发了但没有掷骰"时，请当成**待 DM 结算**，而不是漏了。

2. **Ready 只存条件，不自动触发、不自动执行。**
   引擎负责：消耗 Action、把触发条件写进 `Combatant.ReadyTrigger`、在自己的下一回合开始时清除。
   是否触发、何时触发、触发后做什么，全由 DM 判断；执行同样是一次 `combat_action`。
   引擎不做"条件字符串 → 事件"的匹配——那需要一套触发器 DSL，且很容易和 DM 的叙事判断打架。

若将来要改成自动，属于**新需求**（需要武器选择规则 + 触发器匹配），不是在 C4 里"补个漏"。

## 18. 死亡豁免与 0 HP 状态机（D1 设计）

### 18.1 现状与要改的地方

现在 `Sheet.VitalStatus` 只有 `Alive / Unconscious / Dead`，0 HP 直接落到 `Unconscious`，**不掷死亡豁免、也没有"已稳定"这一态**。这会让"倒地"与"已经稳定"在数据上无法区分。

改为四态，`Unconscious` 不再作为生命状态（它由 `Dying`/`Stable` 派生，只用于对外描述）：

| 状态 | 含义 | 对外文案 |
| --- | --- | --- |
| `Alive` | HP > 0 | 正常 |
| `Dying` | HP = 0 且未稳定，每回合开始掷死亡豁免 | `昏迷（濒死 1/3）` |
| `Stable` | HP = 0 但已稳定，不再掷死亡豁免 | `昏迷（已稳定）` |
| `Dead` | 死亡 | `死亡` |

`Sheet.DeathSaves { Successes, Failures }`（0–3）。

### 18.2 迁移规则

1. **进入 Dying**：HP 降到 0，且不满足 massive 条件 → `Dying`，`DeathSaves` 清零。
2. **massive damage**：单次溢出伤害 ≥ 最大 HP → 直接 `Dead`（与 §15.2-3 一致，不经过 Dying）。
3. **回合开始**：先处理状态到期递减（`ConditionRounds`），再掷死亡豁免——顺序固定，避免"到期的状态还影响豁免"。
4. **死亡豁免**（d20，无加值）：
   - natural 20 → 回复 1 HP，转 `Alive`，清空 `DeathSaves`；
   - 10–19 → 成功 +1；1–9 → 失败 +1；natural 1 → 失败 +2；
   - 成功累计 3 → `Stable`（**同时清零成功/失败**）；失败累计 3 → `Dead`。
5. **Dying 中受伤**：任何伤害 → 失败 +1；若来自暴击 → +2；若该伤害 ≥ 最大 HP → 直接 `Dead`。
6. **Stable 中受伤**：稳定时计数已清零，受伤按"0 HP 受伤"记 1 次失败（暴击 2 次）并回到 `Dying`；massive 仍直接 `Dead`。
7. **治疗**：任意治疗量（≥1）→ `Alive`，清空 `DeathSaves`。
8. **医学稳定**：`Medicine DC 10`（一次动作）→ `Stable`，并清零成功/失败。

> **清零只有两个触发点**：regain any Hit Points 或 become Stable（PHB p.197，2024 措辞一致：
> "The number of both is reset to zero when you regain any Hit Points or become Stable."）。
> 因此 **"3/3 成功 + 1/3 失败"这种状态不可能存在**——成功满 3 就已是 `Stable`，而 `Stable` 必须清零。
> 实现时两条稳定路径（3 次成功、Medicine）都要清零；`SheetStore.Stabilize` 与 `DeathSaveEngine` 不能各写一套。

### 18.3 事件

复用 `kind=check`（`kindType=death-save`，`ability` 留空、`dc` 留空）+ 一条状态迁移事件：

```jsonc
{"kind":"check","checkId":"chk-9","actor":"ella","kindType":"death-save",
 "roll":{"natural":12,"modifier":0,"total":12,"success":true},
 "successes":1,"failures":2,"statusAfter":"dying"}

{"kind":"combat-status","encounterId":"enc-1","actor":"ella",
 "from":"dying","to":"stable","reason":"death-saves","round":3}
```

### 18.4 对现有实现的影响（动手前必须先知道）

- `VitalStatus` 枚举值变化 → `SheetStore`、`combat-hp.json`、对外文案、所有断言 `Unconscious` 的测试都要改；
- `combat-hp.json` 只能表达"打到 0"，需要新增 dying / stable / dead 三个 probe 场景；
- `RoleplaySession` 里"目标倒地（昏迷）"的文案要按新四态分派。

### 18.5 验收

- probe 能跑出：`12 → 1 → 0（dying）` → 回合开始掷豁免 → 3 次失败（dead）；
- 另一条：3 次成功后转 `stable`，再受伤回 `dying`；
- 治疗 1 点 → `Alive` 且 `DeathSaves` 清零；
- natural 20 回 1 HP、natural 1 记 2 次失败各一例；
- 同 seed 可重放。

## 19. 法术位与施法校验（D2 设计）

### 19.1 数据结构

```csharp
Sheet.SpellSlots: IReadOnlyDictionary<int, SpellSlot>   // level 1..9
SpellSlot { int Max, int Used }
```

### 19.2 `CastSpell` 校验顺序（固定）

1. 法术存在（按 `spells` 的 `id` 或 `name` 查）→ 否则 `unknown-spell`；
2. `level == 0`（戏法）→ 不消耗槽，直接结算；
3. `castAtLevel < spell.level` → `slot-too-low`；
4. `slots[castAtLevel].Used >= Max` → `no-slot`；
5. 通过 → **先结算（攻击/豁免/治疗），结算成功才 `Used += 1`**；结算失败不扣槽（宁可重试，不白扣）。

没有 `SpellSlots` 表的角色（非施法者）→ `not-a-spellcaster`，不猜环级。

> **分层职责（与实现对齐）**：引擎的 `ValidateSpell` 只做前两关（法术存在、戏法），槽位检查与会话层的提交顺序在会话层。
> 于是失败路径只有一条：**失败一律回滚行动经济、不扣槽、不落 `kind=damage`**。
> 若 `SpendSlot` 自身返回失败（理论上已被 `CanSpendSlot` 挡住），必须记一条警告或事件，**不允许静默**——
> 否则一旦并发或 Sheet 被中途改写，就会变成"法术放出来了但槽没扣"。

### 19.3 升环伤害

- `scaling.perLevel`（如 `1d6`）：伤害 = 基础骰 + `(castAtLevel - spell.level)` 段 `perLevel`；
- `scaling.variants`（戏法等级档）：按 `castAtLevel` 选对应项；戏法用**角色等级**，映射表放代码（不塞进数据包）；
- 两者都缺省 → 按基础伤害，事件里标 `scalingApplied: false`。

### 19.4 休息

- **长休**：所有槽 `Used=0`、HP 回满、`DeathSaves` 清零、`Conditions` 清空（DM 标记"跨休"的除外）；
- **短休**：默认**不恢复法术位**；Warlock 的 Pact Magic 需要职业字段，`Sheet` 现在没有，明确"暂不支持"，不静默假装恢复。

### 19.5 验收

- 3 环槽用尽后再放 Fireball → `no-slot`；
- 用 4 环槽放 Fireball → 消耗 4 环槽，伤害 `8d6 + 1d6`；
- 戏法连放不消耗槽；
- 长休后槽与 HP 恢复；
- 非施法者施法 → `not-a-spellcaster`。

**验收结果：见 §23.3（五项全部 probe 实测通过，`combat-spellslots.json` 同 seed 两次逐字节一致）。**

## 20. `DmOverride` 契约（D3 设计）

### 20.1 请求

```jsonc
{ "encounterId": "enc-1", "target": "goblin-1",
  "field": "hp", "value": 0, "reason": "DM 判定它直接倒下" }
```

**允许字段白名单**（其余一律拒绝，并在错误里列出支持项）：

| field | value 形态 | 说明 |
| --- | --- | --- |
| `hp` | int | 走与伤害相同的迁移逻辑（0 → Dying，massive → Dead） |
| `tempHp` | int | 直接设置 |
| `maxHp` | int | 直接设置（不改当前 HP） |
| `ac` | int | 直接设置 |
| `status` | `alive\|dying\|stable\|dead` | 直接设置，**不改 DeathSaves** |
| `condition` | `{name, rounds? \| remove:true}` | 加/减状态 |
| `initiative` | int | 改先攻后重排，不打断当前回合 |
| `budget` | `{action?, bonus?, reaction?, movementFeet?}` | 改当前回合资源 |
| `dc` | int | 只对指定 `checkId` 生效 |

### 20.2 事件

```jsonc
{"kind":"combat-override","encounterId":"enc-1","target":"goblin-1",
 "field":"hp","from":5,"to":0,"reason":"DM 判定它直接倒下","seq":412}
```

- `from` 由引擎填当前值，调用方只给 `to`；
- 事件自带 `from/to`，重放时直接应用，**不重新校验**；
- override 与引擎校验冲突时 override 胜，并记 `overridden: true`。

### 20.3 边界

- override **不触发**自动叙事，说书人仍要自己描述结果；
- 不允许改 `Encounter.Phase` 或强行跳回合（那是 `EndCombat` / `EndTurn` 的职责）；
- 所有 override 进 `story.jsonl`，审计可查。

### 20.4 验收

- 改 HP 到 0 → 状态迁移为 `Dying`（不是直接 `Dead`）；
- 改 `status` 到 `dead` → HP 不变但状态为 `Dead`；
- 重放日志后 `Encounter` 与 `Sheet` 快照逐字段一致；
- 未知字段 → 拒绝且事件里写明支持列表。

**验收结果：见 §24.3（四项 probe 实测通过，`combat-override.json` 同 seed 两次逐字节一致）。**

## 25. 工具表变更与前缀缓存（P1 设计）

### 25.1 为什么单独一节

系统提示前缀（base prompt + tools + memory）必须跨轮**字节稳定**，否则每轮都会打破 DeepSeek 的前缀缓存。工具表与工具说明都属于前缀的一部分，因此**加工具、改说明、改调用时机段落，都是前缀变更**。

MeetingRoom 在阶段 2 已实现「前缀指纹」；工具表变化 → 指纹变化 → **下一次请求一次性 cache miss**，随后恢复。所以不是"不能改"，而是要把 miss 收敛成**可预期的一次**。

### 25.2 规则

1. **批次化**：一批把所有要加的工具与说明一次改齐，不分三次加、miss 三次。
2. **指纹与版本号同步更新**：让这次 miss 可解释，而不是"命中率莫名其妙掉了"。
3. **实施记录写明**：本节对应的批次导致一次预期 miss，便于以后对照 `CacheDiagnostics`。
4. **说明文案与工具同批改**：`description` 也是前缀，改文案同样会 miss。
5. **运行时不动态增删**：除已有的按会话启用/隐藏逻辑（角色集群的 `hidden` 集合）外，不在运行中改工具表。

### 25.3 本批要接入的工具

| 工具 | 时机 | 关键约束 |
| --- | --- | --- |
| `dm_override` | **仅当导演明确要求**改数值/状态时 | 不得自行改数；必须带 `reason`；改动留痕；不接受"我判断这样更好" |
| `start_combat` / `combat_action` / `next_turn` / `end_combat` | 进入/推进/结束战斗 | 已在 C1–C4 注册，本批复核说明是否完整 |
| `request_check` | 需要检定（游说/洞悉/察觉/巧手…）且**有失败后果**时 | DC 来源须标明；暗骰不报数值；同一理由不重复刷 |

### 25.4 提示词要点（新增段落）

- **何时开战**：玩家明确进入对抗、且需要逐回合结算时才 `start_combat`；叙事冲突可用单次检定解决，不要一律开战。
- **意图翻译**：角色 Agent 的意图 → 一条 `combat_action`（目标、武器/法术、理由）；一次只提一个动作，不做"连环三招"。
- **被拒如何叙述**：读 `rejected.message` 的原文要点（"目标在 60 尺外，弯刀只能打到 5 尺"），不要说"系统不允许"。
- **暗骰**：只叙述角色能感知的部分；不得出现 DC、骰值、成败判定。
- **数值权威**：所有数值来自工具回执；禁止自行加血、改命中、编造伤害。
- **`dm_override`**：只在导演明确说"把它改成 X"时调用；不要用 override 绕过规则给 AI 自己方便。

### 25.5 验收

- `--probe-tools`（新增，仿 `--probe-rules`）：打印当前工具清单 + 前缀指纹哈希；同一构建多次运行哈希一致。
- 工具说明里不得含时间戳、随机数、会话 id 等会变化的内容。
- 本批落地后记录一次**预期 miss**；下一轮缓存诊断应恢复正常。
- 单测：工具名集合与说明非空；`dm_override` 未在非导演上下文被注册（沿用现有权限判定）。

## 26. Sheet 来源（S1 设计）

### 26.1 问题（端到端实测暴露）

`SheetStore` 为空时，攻击能命中、伤害能算，但**扣不下去**——回执是「数值表里没有「ella」，伤害没有扣」。
角色卡目前只有文本，没有 HP/AC；而 `monsterTemplates` 按既定设计**不含数值**。所以必须明确"数值表从哪来"。

### 26.2 来源与优先级

| 优先级 | 来源 | 适用 | 说明 |
| --- | --- | --- | --- |
| 1 | `roles/<id>.sheet.json`（角色卡旁路文件） | 玩家角色 | 会话启动时预加载 |
| 2 | `start_combat` 的 per-combatant `sheet` 参数 | 怪物 / NPC | 覆盖第 1 层，DM 或说书人填 |
| 3 | **无表** | 临时角色 | 允许参战、不扣 HP，回执必须明说 |

**不做**：从 `monsterTemplates` 自动生成数值——模板只有 `cr/type/size`，这是 V3 的既定决定，别在这里开倒车。

### 26.3 `sheet.json` 形状

与 `Sheet` 的 JSON 形状一致，直接反序列化：

```jsonc
{
  "characterId": "ella",
  "maxHp": 30, "currentHp": 30, "tempHp": 0,
  "ac": 15,
  "abilities": {"str":10,"dex":16,"con":14,"int":12,"wis":13,"cha":10},
  "saves": {"dex":5,"con":2},
  "skills": {"perception":5,"insight":3},
  "profBonus": 2, "level": 3,
  "spellSlots": {"1": {"max":2,"used":0}},
  "weaponAttacks": [{"name":"Longsword","ability":"str","proficient":true,
                     "damageDice":"1d8+3","damageType":"slashing","mastery":["Sap"]}]
}
```

**字段名口径（定稿）：简写与规范名都接受，规范名优先。**
`Sheet` 的内部字段是 `armorClass` / `strength`…（`Ability` 全名）/ `proficiencyBonus`，但角色卡是**手写**的，
玩家说“AC 15、力量 16”比 `armorClass` / `strength` 自然得多。因此在 JSON 边界做别名映射：

| 简写 | 规范名 |
| --- | --- |
| `ac` | `armorClass` |
| `str / dex / con / int / wis / cha` | `strength / dexterity / constitution / intelligence / wisdom / charisma` |
| `profBonus` | `proficiencyBonus` |
| `level` | **不存在**（`Sheet` 没有等级字段，写卡时不要填；需要时另开字段） |

两份名字同时出现且值不同 → **拒绝该表并报错**（不静默取其一）。这不是"多一层解析"的负担，
而是让写卡的人不必记住内部命名。

### 26.4 加载期校验（关键）

- **会话启动时就要校验**，缺必填字段（`maxHp`、`ac`、六属性、`profBonus`）**当场报错并写进启动诊断**；
  不允许"能扣血但检定算不了"的半残表——那种错误会拖到战斗中才炸，比启动时直接拒更坑。
- JSON 解析失败 → 记警告、该角色视为无表，**不崩会话**。
- `start_combat` 的 per-combatant `sheet` 同样校验；不合格就拒绝参战并说明缺项。

### 26.5 `dm_override` 与无表

- 有表：正常改（§20 白名单）。
- 无表：允许 `dm_override` **创建最小表**（至少 `hp/maxHp/ac`），事件里标 `createdSheet: true`；
  这样 DM 不必先去改文件才能救场。若选择拒绝创建，回执必须明确"没有数值表"。

### 26.6 验收

- 角色卡带 `sheet.json` → 启动后 `SheetStore` 有数据 → 攻击能真正扣血；
- `start_combat` 带 per-combatant `sheet` → 怪物 HP 生效；
- 缺必填字段 → 启动诊断报错，不进入战斗；
- 无表 → 回执「没有数值表，伤害未扣」；
- 坏 JSON → 警告 + 视为无表，不崩会话。

## 27. `ToolSignature` 必须包含参数 schema（P2 修正）

### 27.1 问题

模型看到的工具定义是 `AITool` 序列化后的 `function` 对象，**包含 `parameters`（JSON Schema：类型 / 必填 / enum / 默认值）**；而 `ContextComposer.ToolSignature` 只拼「类型:名:说明」。

后果：

1. 参数变更**真会改变前缀**（真实 cache miss）；
2. `--probe-tools` 指纹**不变**——P1 补七个 `combat_action` 参数就是活例（两次指纹完全一致）；
3. 最坏的是**"批次化 + 指纹对账"会报告"没变"**，让人误以为前缀没动。

### 27.2 修法

- `ToolSignature` = 工具名 + 描述 + **规范化后的参数 schema**；
- **规范化必须做**：属性按名称排序、去掉运行时元数据、不写字典插入顺序——否则同一 schema 的键顺序差异会造假阳性，比漏报更难查；
- baseline / runtime 两个口径继续分开（§25.6）。

### 27.3 验收

- 同一构建连跑两次 `--probe-tools` 哈希一致；
- 改一个参数名 / 必填性 / 枚举值 → 哈希变化；
- **只改字典插入顺序（内容不变）→ 哈希不变**；

## 31. 踩过的坑（工程笔记，2026-10-27）

这些不是设计决策，是**实际花过时间才找出来的**，写在这里免得下一批重踩。

### 31.1 事件表是唯一契约，漏一个类型不会报错

`wwwroot/js/stream.js` 的 `EVENT_TYPES` 决定前端订阅哪些事件；后端发出去的类型如果不在这张表里，
前端**收不到也不报错**——表现就是"界面没反应"，没有任何日志。

F1 就是这样栽的：`roleplay.warning` 与 `roleplay.combat` 都漏了，前端既不显示警告、战斗条也不刷新，
而我在面板模块里找了两轮事件绑定才发现根子在白名单。

**纪律**：后端新增/改名任何 `Publish("...")` 类型，**同批**改 `stream.js` 的 `EVENT_TYPES`。
更硬的约束（将来可选）：让 `--probe-tools` 顺带打一份"后端事件类型清单"，与前端白名单对账。

### 31.2 `dotnet run --no-build` 不刷新 `wwwroot/` 副本

`csproj` 用 `Content Include="..\..\wwwroot\**"` 把仓库根的 `wwwroot` 复制到 `bin/Debug/net10.0/wwwroot`，
而 Host 由 `UseStaticFiles()` 读的是**副本**。用 `--no-build` 起服务时副本一直是旧的——
改了前端却"界面没反应"，很容易误判成逻辑写错。

**做法**：改前端后 `dotnet build` 一次，或 `cp -r wwwroot/. src/MeetingRoom.Host/bin/Debug/net10.0/wwwroot/`。
（`MeetingRoom/AGENTS.md` 里有同一条。）

### 31.3 角色 / 数值表的 id 必须大小写不敏感

说书人写 `Ella`、角色卡是 `ella`：`SheetStore` 与 `RoleplayStrategy._actors` 原本都用 `StringComparer.Ordinal`，
于是"表明明存在，伤害却扣不下去"（回执是「数值表里没有 Ella」）。两者都已改 `OrdinalIgnoreCase`。
**口径**：id 是标识符，查找一律大小写不敏感；排序（先攻平手）仍用 `Ordinal`。

### 31.5 前端模块崩了，页面会只剩静态 HTML

`main.js` 里把点击委托插在 `const combatPanel = …` 之前，触发 **TDZ**：
`Cannot access 'combatPanel' before initialization` —— 整个模块求值失败，
页面表现是「只有静态 HTML、侧栏空白、什么按钮都没反应」。同一批还踩了变量重名
（`panel-combat` 里新加 `board` 与原有的 `tactical-board` 元素变量同名）导致 `SyntaxError`。

**判断顺序**：看到"页面只剩静态 HTML / 侧栏空白"，**先看 console 的第一条报错**，
不要从 CSS 或 DOM 结构查——模块级语法/初始化错误不会留下任何 DOM 痕迹。

### 31.6 只读 TEMP 环境下 multipart 上传必失败

`ReadFormAsync` 对超过阈值（默认 64KB）的 form 会把 body 落到 `%TEMP%\ASPNETCORE_*.tmp`。
受限环境里 TEMP 可能不可写（本项目沙箱就是），表现为 `UnauthorizedAccessException` +
连接被重置，日志还会跟着写不进去（"Cannot open log file"），很容易误判成上传逻辑错。

**做法**：上传端点同时支持**原始字节**通道（非 multipart 时直读 `request.Body`），
脚本用 `curl --data-binary @file "…/upload?name=x.webp"`。两条通道必须汇入**同一个**
`ImportAsync`（宽高只认字节头、id 白名单同一套），不能一条严一条松。

### 31.4 用 Python 脚本改 C# 里的字符字面量转义会被吃掉

`heredoc` 传进来的双反斜杠转义到 C# 里会变成真实换行，编译器报一串「常量中有换行符」。
**做法**：含反斜杠的 C# 字面量（如 `builder.Append('\n')`）改用 `edit_file` 直接写，别过 Python 字符串。
（讽刺的是，写这一节时我又踩了一次——正文里的转义被折成了真换行。）

### 37.1 `--probe-check-spam`：不依赖模型愿不愿意连调

直接构造一个 `RoleplaySession`（假 `IChatClient` + 计数总线 `CountingEventBus`），连调三次同参 `RequestCheckAsync`：

三条断言分别对应：**不落 check 记录**（第 3 次没有）、**不进检定流**（publish 只 3 次 = 2 主动 + 1 被动）、

### 41.2 根因（上一批的设计缝隙）

### 43.2 为什么改（用户决策）

p6 那句"拿不到回执就不要把伤害写进正文"**实测无效**，而且**判据本身就错了**：
跑团里 DM 经常描述擦伤不扣血，那是常态，不是 bug。真正有害的是**声称机制性结果**——
"他倒下了""这一刀要了她的命"——那会让正文与 HP 脱节，玩家会以为对方已经倒下。

所以收窄为：

```
- 战斗中写受伤要分清两种：擦伤、流血、皮肉伤这类描写可以直接写；
  但机制性结论——谁倒下、失去意识、死亡、HP 归零、彻底丧失行动能力——
  必须由 combat_action 的伤害回执支持。拿不到回执时，只能写擦伤与侥幸脱开，
  不能写倒下或“这一刀要了她的命”。
```
