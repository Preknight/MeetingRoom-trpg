# 叙事模式：前台上下文与后台观察设计

> 修订记录：
> - 2026-10-29 11:20 初版：前台三层上下文、`recall_story` 工具、后台观察页与 DM 提醒通道。
> 决策来源：2026-10-29 11:09 提出的两项改造与随后三项选择（纯展示页 / 三层上下文 / 复用待审批弹窗）。

---

## 0 为什么改

叙事模式现在把三类东西全塞进**共享节**（= 系统提示的一部分）：

```
世界观 / 当前情境 / 导演身份 / 剧情进度      ← 稳定
[此刻的现场]  时间·地点·在场名单            ← 会变
[最近发生]    最近 6 条，每条截断 200 字符    ← 滚动
```

而 `[最近发生]` 是**滚动窗口**（`RemoveAt(0)`）。前缀缓存按**字节前缀**匹配，
每加一条就把第一行挤掉 → 整段文本逐字变化 → **每轮都 miss**。

用户最初判断「已发言内容固定，缓存命中率高」——这个判断方向对，但**当前实现恰好相反**。
把 6 条改成 60 条只是把「每轮失效」变成「每 60 条失效一次」，不解决根本问题。

---

## 1 前台：三层上下文

核心思路是**把会变的东西从「前缀」挪到「只追加的消息序列」**。

| 层 | 内容 | 位置 | 何时变化 |
| --- | --- | --- | --- |
| **L1 前缀（稳定）** | 世界观 / 情境 / 导演身份 / 角色卡 / 工具签名 / **早期剧情摘要** | system + 共享节 | 只在「摘要更新」时变一次 |
| **L2 剧情消息（追加）** | 摘要点之后到现在的**全部**剧情发言 | 对话消息（user/assistant） | 只追加，从不修改 |
| **L3 摘要（压缩）** | 比 L2 更早的内容压成一段固定文本 | 共享节的一部分 | 触发压缩时更新，之后稳定 |

### 1.1 关键约束

- **L2 不滚动**。达到阈值前一条都不删；滚动会毁掉前缀缓存，这是这次要改掉的核心问题。
- **压缩发生在 L3**：当 L2 超过阈值（默认 80 条，或估算 token 超 8000）时，
  把 L2 最前面的约一半压成摘要追加进 L3，L2 只剩后半段。
  压缩是**低频事件**，每次只造成一次 cache miss。
- 每条剧情仍然截断 200 字符（用户确认合理：角色扮演不需要长篇大论）。
- `[此刻的现场]` 从共享节**移出**，改为独立的消息段（或「变了才更新」的独立段）——
  它每次都变，放在前缀里等于每天重建前缀。

### 1.2 摘要怎么生成

第一版用**规则摘要**：取被压缩段的每条发言的前 60 字符，按角色归并成
「Ella 在第 3–8 幕：发现了地窖、拿到钥匙…」。不调用模型，零额外 token。

后续如果质量不够，再考虑用一次模型调用生成。

### 1.3 配置

```
roleplay.context.historyLimit        80     // L2 上限条数
roleplay.context.historyTokenBudget  8000   // 或按 token 估算，先到先生效
roleplay.context.compressRatio       0.5    // 压缩时压掉前半段的比例
roleplay.context.lineChars           200    // 单条截断
```

## 2 工具：`recall_story`（查落盘记录）

角色与说书人都挂。**只读**，不改变「只请求不结算」的边界。

```jsonc
{
  "query": "钥匙",          // 可选，关键词（在正文里匹配）
  "author": "Ella",         // 可选，只看某个角色
  "kinds": ["speech"],      // 可选：speech|world|roll|request|check|combat|warning
  "since": 12,              // 可选，从第几幕之后
  "last": 20                // 可选，最近 N 条（默认 10，上限 40）
}
```

返回：按时间正序的纯文本行 `第 N 幕 · Ella：……`，总长超过 2000 字符时截断并标注。

**限流**：一轮一次（与 `_ruleLookupsThisRound` 同款机制），否则模型会拿它代替记忆。

数据源就是 `story.jsonl`（已有 `speech / world / roll / request / check / interaction / warning /
combat.*` 这些 kind），不需要新落盘。

## 3 后台：观察页与 DM 提醒

用户选择：**先做纯展示页，AI 接入留到以后**。所以后台是一个**只读观察 + 手动提醒**的页面，
不内建常驻 Agent。

### 3.1 观察面（API）

```
GET /api/roleplay/backstage?since=<revision>&limit=200
```

返回自 `since` 以来的事件（按 revision 升序）：

```jsonc
{
  "revision": 42,
  "events": [
    { "revision": 40, "kind": "speech", "author": "Ella", "text": "..." },
    { "revision": 41, "kind": "narrator_thought", "text": "...", "tool": null },
    { "revision": 41, "kind": "tool_call", "name": "look_around", "args": {...}, "result": "..." },
    { "revision": 42, "kind": "world", "state": { "time": "...", "place": "...", "present": [...] } }
  ]
}
```

**数据缺口**：说书人的**思考过程与工具调用目前没有落盘**——只在前端 `store.backstage` 内存里，
刷新就没了（`panel-backstage.js` 的注释已承认这点：「旧记录仍在落盘的 transcript 里，阶段 3 提供」）。

所以要新增一个**独立的落盘文件**（不要塞进 `story.jsonl`，避免污染剧情时间线）：

```
data/stories/<id>/backstage.jsonl
```

记录：

```jsonc
{ "rev": 41, "at": "2026-10-29T03:20:11Z", "kind": "thought", "who": "narrator", "text": "..." }
{ "rev": 41, "at": "...", "kind": "tool", "who": "narrator", "name": "dice_roll", "args": {...}, "result": "..." }
{ "rev": 41, "at": "...", "kind": "tool", "who": "ella", "name": "look_around", "args": {...}, "result": "..." }
```

滚动保留（默认最近 2000 条），避免无限增长。

### 3.2 呈现面（页面）

独立页面 `/backstage.html`（与 `/map-editor.html` 同级），三栏：

| 栏 | 内容 |
| --- | --- |
| 左 | 前台剧情（`story.jsonl` 的 speech，按幕） |
| 中 | 后台动态（thought / tool，按幕对齐） |
| 右 | 提醒输入框 + 当前世界状态 + pending 列表 |

顶栏有「跟随最新」开关（自动滚动）与「只看某角色」过滤。

### 3.3 提醒面（复用待审批）

用户选择：**复用第五列的说书人弹窗机制**（pending）。

```
POST /api/roleplay/dm-note
{ "severity": "warn", "text": "Ella 上一幕不该知道钥匙在井里" }
```

写入 `PendingDecisionKind.DmNote`，出现在第五列「待确认事件」，DM 在前台就能看到并处理：

- 「知道了」→ 记录 ack，不改变任何状态
- 「记进设定」→ 追加到 L3 摘要段（长期生效）
- 「忽略」→ 关闭

**超时策略**：与迷雾提议不同，DM 提醒**超时默认不生效**（它只是提醒，不该有副作用）。

### 3.4 以后接 AI

观察面与提醒面都是纯 HTTP，所以以后接外部 AI 只需：

1. 轮询 `GET /backstage?since=`（或用 SSE 推送）
2. 分析后 `POST /dm-note`

不需要在 MeetingRoom 内跑常驻模型。这也是用户选「纯展示页」的原因——先把接口和体验做出来，
AI 何时接入、用什么模型，以后再说。

## 5 验收要点

**B1**

- 同一场景连续 10 轮，`--probe-tools` 的前缀指纹**只在压缩发生时变一次**（其余轮次不变）；
- 第 81 条触发压缩后，L2 降到约 40 条、L3 摘要出现且内容合理；
- 角色仍能接上前文（抽查：第 70 轮提过的东西，第 75 轮还能被引用）。

**B2**

- 查「钥匙」能命中若干条；`author=Ella` 只返回她的；`last=5` 只回 5 条；
- 一轮调两次，第二次被拒；查询不改变剧情状态。

**B3–B5**

- 说书人的 thought 与 tool 调用在 `backstage.jsonl` 里可查，重启后仍在；
- `/backstage` 页面能同时看到前台与后台，按幕对齐；
- `POST /dm-note` 后第五列出现卡片，且**不影响剧情推进**；三种回应都只改自身状态。

## 6 实施记录（B1 + B2，2026-10-29 11:30）

本批只做 B1（前台三层上下文）与 B2（`recall_story`）。B3–B5 未动（后台落盘 / 页面 / DM 提醒）。

### 6.1 B1 落地成了什么样

| 层 | 实际位置 | 何时变 |
| --- | --- | --- |
| **L1 前缀** | `system prompt` + 共享节（世界观 / 情境 / 导演身份 / **L3 摘要**）+ 工具签名 | 只在压缩时变 |
| **L2 剧情消息** | 共享节之后、角色节之前的独立 `user` 消息（每条发言一条） | 只追加，永不修改 |
| **角色节（尾部）** | 角色卡 + 私有状态 + 地图 + 战斗 + **现场与进度** + 图 | 每轮变，但不在前缀里 |
| **L3 摘要** | 共享节里的 `[早期剧情摘要]` | 压缩时追加一段 |

关键改动（`RoleplaySession` / `ContextComposer` / `ComposeRequest`）：

- 删掉 `_recentLines`（6 条滚动窗口 + `RemoveAt(0)`），换成 `List<HistoryLine> _history`：
  **只追加**，单条按 `roleplay.context.lineChars`（默认 200）截断。
- `ComposeRequest` 新增 `History`；`ContextComposer.Compose` 把它排成
  `[system][共享节][L2 逐条 user][角色节][私有历史][本轮任务]`。
- `[此刻的现场]` 与「剧情进度：第 N 幕」**从共享节移出**，进角色节（`SceneSection()`）——
  它们每轮都变，留在前缀里等于每轮重建前缀。
- 压缩：`_history.Count > historyLimit（80）` 或估算 token > `historyTokenBudget（8000）` 时，
  把前 `compressRatio（0.5）` 压成**规则摘要**（每条前 60 字符、按作者归并，不调模型）追加进 L3，
  L2 只剩后半段。压缩是低频事件：一次只造成一次 cache miss。
- L3 摘要落盘到 `context-summary.json`（与 `story.jsonl` 同级），构造会话时读回；
  坏文件只当作"没有摘要"，不拖垮会话。
- **前缀指纹的口径**（重要）：只覆盖 L1（系统提示 + 共享节 + 工具签名），**不含 L2**。
  理由：provider 的前缀缓存按 token 前缀匹配，**末尾追加不会让已缓存部分失效**；
  把 L2 算进指纹反而会让"不压缩的轮次指纹也变"，与验收口径相反。
  L2 的稳定性由另一条不变量保证——**只追加、不滚动**，探针直接逐轮比对快照前缀。

### 6.2 B2 落地成了什么样

- 工具 `recall_story`：进 `Narrator.ToolNames` 与 `Narrator.CharacterToolNames`（角色 6 → 7）。
- 参数：`query`（正文子串）/ `author` / `kinds`（`speech|world|roll|request|check|combat|warning`）/
  `since`（从第几幕起）/ `last`（默认 10，**上限 40**）。
- 数据源就是 `story.jsonl` 的内存视图（`StoryTimeline`），**没有新增落盘**；
  非发言记录（world / roll / check / request / warning / combat.*）没有自己的 revision，
  按"落在哪一幕之后"归到最近一个 turn，这样 `since` 过滤与显示用同一把尺子。
- 回执：`第 N 幕 · 谁：……` 按时间正序；总长超 **2000 字符**截断并标 `[truncated]`；
  开头一句「只读回忆，共 N 条；它不改变任何状态」。
- **见证者过滤**：角色只回忆得到自己见证过的发言（`StoryLine.Witnesses` 空 = 公开），说书人看全量。
- 限流：`_storyRecallsThisRound`，一轮一次（`SayAsync` 每轮 `ResetStoryQuota()`），
  第二次回"本轮已经回忆过一次了"。**不占**规则查询的 3 次额度，也不占"一轮一个请求"的额度。
- 工具描述写清了「用于忘掉前文时复查，不是每次发言前都查」。

### 6.3 配置（`meetingroom.json`）

```jsonc
"roleplay": {
  "context": {
    "historyLimit": 80,        // L2 上限条数
    "historyTokenBudget": 8000, // 或估算 token，先到先生效
    "compressRatio": 0.5,      // 压缩时压掉的比例
    "lineChars": 200           // 单条截断
  }
}
```

`ConfigLoader` 里三件事一起做了：已知键（`roleplay.context`，**三层键写错也会提示**）、
校验（limit ≥ 1、token > 0、ratio ∈ (0,1)、lineChars > 0）、默认值（缺项自动补齐，写默认文件时带出来）。

## 7 实施记录（B3 + B4，2026-10-29 11:53）

### 7.1 B3：`backstage.jsonl` 与 `GET /api/roleplay/backstage`

- 新文件 `data/stories/<id>/backstage.jsonl`（与 `story.jsonl` 同级、**不混在一起**：
  剧情是权威状态、要能重放；后台是观察旁路，塞进去会污染时间线）。
- 一条记录的字段照 §3.1：`{ rev, at, kind, who, name?, args?, result?, text? }`；
  `kind` 只有 `thought` 与 `tool`；`rev` 用**即将提交的那一幕**（`_timeline.Revision + 1`），与前台幕号对齐。
- **产生点落盘**，不是事后扫描：`ParticipantRegistry` 的 turn callbacks 里多了一个可选出口
  `ParticipantRegistryOptions.Backstage`（`Action<BackstageSignal>`）。叙事会话传进去，会议模式不传
  ——会议侧行为一个字节都没变。
  - `thought`：`ThoughtDelta` 是流式的逐段文本 → 按 `(who, turn)` 攒成一条，在**工具调用前**、
    **每轮结束**（`SayAsync` 早退路径之前）flush；`kind=thought`。

## 8 实施记录（B5，2026-10-29 11:58）

### 8.1 落成了什么

- `PendingDecisionKind.DmNote`（线缆名 `dm_note`）：提醒走既有的待决机制，第五列「待确认事件」直接显示。
- `POST /api/roleplay/dm-note`，body `{ severity: "info"|"warn", text }`：
  - 校验：`severity` 只收 info / warn；`text` 非空、**上限 500 字符**（`RoleplaySession.DmNoteMaxChars`）；
    失败回 400 + 原因，成功回 `{ ok, id, message }`（`id` 就是第五列那张卡片的 id）。
  - 卡片三个选项：**知道了**（`ack`）/ **记进设定**（`apply`）/ **忽略**（`ignore`），默认 `ack`。
- 三种回应的语义（答复走既有的 `POST /api/interactions/{id}`，前端不加新端点）：

| 选项 | 效果 |
| --- | --- |
| 知道了 | 只 ack，**不改任何状态**（revision / 摘要 / 世界都不动） |
| 记进设定 | 往 L3 摘要追加一行 `- 导演提醒（第 N 幕）：……`（`warn` 写「导演警告」），**长期生效**；revision 不动 |
| 忽略 | 关闭卡片，什么都不改 |

- **超时 = 「知道了」**：`interaction.timeoutSeconds` 复用在这里，超时用默认选项收口——
  提醒本身没有副作用，所以超时只能是"没人看到"，**绝不自作主张改世界**。

### 8.2 三条硬约束怎么落地的

1. **不暂停剧情**：新加了 `SessionCore.RegisterSideDecision(...)`——只 `_decisions.Open` + 广播
   `interaction.request`，**不 `EnterAwaitingLocked`、不 await**。所以 `WaitWhileBlockedAsync` 不会挂住，
   投完提醒当场可以继续 `say`（探针实测：投递后一轮照跑，第 0 幕 → 第 1 幕）。
2. **不进说书人上下文**：`AddDmNote` 不写共享节、不写 L2、不写角色节——探针逐项断言
   「共享节 / L2 / L3 摘要都不含这条提醒」，并在**跑完一轮之后**再断言一次。
   唯一的例外是用户自己点「记进设定」：那是**导演明确要求记住的设定**，进 L3 是其语义；
   除此之外它一个字都不会流进说书人的提示词。
3. **不影响前缀指纹**：工具面与静态前缀四个值不变（见 §8.4）。运行时的 L1 指纹只在
   「记进设定」被点过之后变一次——这是该选项的语义，不是 B5 的副作用。

### 8.3 顺手修掉的一个真问题：收口回调的时序

第一版用 `decision.Completion.ContinueWith(...)` 处理回应。`PendingDecision` 的 TCS 带
`RunContinuationsAsynchronously`，所以"点了按钮"到"摘要真的写进去"之间有一个**窗口**——
探针第一次跑就抓到了：`applied=True` 但摘要仍是 0 字符（稍后才落地）。

改法：`PendingDecisionRegistry.Open` 增加可选 `onResolved` 回调，在 `Complete(...)` 里

现在"答复返回"与"业务状态落地"是同一件事，不会出现 UI 说成功、状态还没改的情况。
会议侧与迷雾提议不传这个回调，行为不变。

### 9.1 A【高】paused 时发导演指令会挂 146 秒 → 改为自动恢复

**根因**：`paused` 与 `awaitingInput` 共用同一道等待门（`SessionCore.WaitWhileBlockedAsync`）。
`paused` 是"说书人建议收束 / 用户手动暂停"后的休眠，`awaitingInput` 才是"正等你拍板"——
两者混在一起，于是发一条指令会一直等到有人点「继续」（真机 146 秒 = 提议超时 120 秒后仍继续阻塞）。

**选型**：**自动恢复**（而不是 409 拒绝）。理由：导演发一条指令的直觉就是"继续往下演"；
弹一个"请先点继续"等于让他多点一次、且在两分半后才看到——那是把机制泄漏给用户。
拒绝也满足"不挂"，但它把本该自动的事变成用户负担。

**实现**：`RoleplaySession.SayAsync` 开头判 `Status == Paused` → `ResumeAsync()` + 推一条
`roleplay.auto-resume`（`reason=director-say`），然后照常处理这条指令。
`awaitingInput` 的语义**不变**：有事项在等拍板时仍然等（那时阻塞是设计，不是缺陷）。

**实测**（`--probe-paused-say`，6/6）：

```
✅ 暂停后状态为 paused                    Paused
✅ paused 时发指令：不挂（20 秒内返回）     **1 ms**（改前 146 秒）
✅ 这条指令被真正处理了（revision 前进）    第 1 幕 → 第 2 幕
✅ 会话已自动恢复（不再是 paused）          Running
✅ 推了一条 roleplay.auto-resume 事件       1 次
✅ 未暂停时不推 auto-resume（只恢复一次）    1 次
```

## 11 实施记录（nudge / idle_beat 去重，2026-11-03 19:52）

### 11.1 真机现场（为什么要改）

用 gemini-3.5-flash 跑一场：**两幕只产出 2 段对话，说书人却调了 14 次工具**
（idle_beat 6 / nudge_character 5 / propose_world_state 2 / request_check 1）。
而 `RunPendingIntentsAsync` 的预算 = `NarratorBeatsPerTurn`（默认 1），每轮只消费 1 个意图，
剩下的堆在队列里——**导演不再发任何指令，20 秒后 revision 自行 1→2**，观众感受是"剧情自己乱跑"。

### 11.2 去重的三个决定

**(1) "同一轮"以 `SayAsync` 为界**（一次导演指令 = 一轮）。理由：

- 说书人一次 turn 里连续多次 nudge 正是要合并的对象——它们天然属于同一轮；
- `_requestsThisRound` / `_checksThisRound` 等既有额度都用这个边界，保持一致；
- 若按"`RunPendingIntentsAsync` 的消费周期"算，跨轮残留的意图会被反复当成"本轮首次"，
  合并语义会随消费节奏漂移。

实现：`SayAsync` 开头（与额度重置一起）清空 `_intentAttempts`。

**(2) 保留首次入队位置，只更新内容**。队列从 `Queue<T>` 换成 `List<T>`：`Queue` 只能入队/出队，
做不到"就地改内容"。执行顺序因此稳定——`A → B → A` 仍是 `A(新内容)、B`，不是 `B、A`。

**(3) 队列上限 = `max(5, 在场角色数 + 1)`，可配**（`roleplay` 侧新增
`RoleplayOptions.NarratorIntentQueueLimit`，0 = 自动）。

- 用户倾向 5，但**多角色场里"每个角色各被点名一次"是合理的**，固定 5 会误伤第 6 个角色。
  所以默认跟着角色数走：5 个角色 → 上限 6（5 次点名 + 1 次描写正好装得下）。
- 上限实际是**防御性**的：键空间就是"每角色一条 nudge + 一条 beat"，正常永远撞不到；
  真撞到时明确拒绝而不是静默丢弃（探针用一个上限=2 的会话专门验这条路径）。

### 11.3 把结果告知模型（这是用户要求的重点）

## 12 实施记录（拆开"复盘"与"自动一拍"，2026-11-03 20:04）

### 12.1 问题：0 原来不是"只写不推进"

用户的原话是"DM 输入量很大且很长，不能 DM 还没介绍完场景说书人就自顾自点名角色推进剧情"。
核对代码后确认用户与规划会话的判断：叙事模式**没有定时器**，推进完全由 `SayAsync` 驱动（DM 打字期间确实不动），
问题出在 `SayAsync` 一轮末尾的 `RunNarratorReviewAsync`——它会执行 `narratorBeatsPerTurn` 个排队意图。

而当时的 `NarratorBeatsPerTurn = 0` **把整个复盘短路掉**：

```csharp
if (_options.NarratorBeatsPerTurn <= 0 || ResolveNarrator() is not { } narrator) return [];
```

于是 `propose_world_state` / `ask_user` / `declare_scene_end` 也一并不做了——那不是"只写不推进"，
是"说书人整个不出现"。`Program.cs` 里旧探针的注释（"`NarratorBeatsPerTurn = 0`——不让复盘那一步真的跑模型"）
就是这个语义的旁证。

### 12.2 拆成两件事

| 概念 | 方法 | 受谁控制 |
| --- | --- | --- |
| **复盘** | `RunNarratorReviewAsync` 主体（说书人看一遍本轮、可提议世界状态 / 提问 / 建议收束） | **始终执行**（只要求解析得到说书人） |
| **自动一拍** | `RunPendingIntentsAsync`（执行排队的 `nudge` / `beat`） | `narratorBeatsPerTurn`（0 = 不执行） |

改动两处：

1. 复盘去掉 `NarratorBeatsPerTurn <= 0` 的短路；
2. `NudgeCharacter` / `IdleBeat` 在 `NarratorBeatsPerTurn <= 0` 时**直接拒绝且不入队**，回执统一为
   `RoleplaySession.NoAutoBeatMessage`：

```
当前不允许说书人自主推进（narratorBeatsPerTurn = 0）：不要点名角色，也不要自主描写；只写你自己的叙述，等导演指示。
```

"不入队"是刻意的：否则队列会永远堆着永不执行的意图，`PendingNarratorIntents` 还会一直非零。

  `roleplay.narratorBeatsPerTurn 不能为负（0 = 只写不推进：复盘照常、但不点名不描写）`）；
- 已进 `KnownKeys["roleplay"]`，写错键会被提示。

**没有改工具描述**（用户明确要求）：否则说书人前缀指纹会再变一次，而且模型的"该不该点名"不该靠描述里的一句话

- `RunPendingIntentsAsync` 的预算仍按条数算（1 = 一轮一拍）；`beats = 2` 的含义不变。
- 会议模式没有这个开关（它的 `NarratorBeatsPerTurn` 概念不存在）。

## 13 实施记录（`declare_scene_end` 引起的 219 秒挂起，2026-11-03 22:24）

### 13.1 现场与三处根因

用户 2026-11-03 22:15 那场（`data/stories/DND世界观-费伦大陆-剑湾北部某不知名的墓穴中`）：

```
14:15:06 declare_scene_end → PauseAsync()
14:15:13 idle_beat          ← 还在跑
14:15:24 declare_scene_end  ← 又 pause
14:15:31 declare_scene_end  ← 第三次
14:15:36 nudge_character
14:15:41 declare_scene_end  ← 第四次，回执都是“已建议收束”
… 3 分钟空白 …
22:18:47 POST /api/roleplay/say - 499 - 219760ms
```

三处根因（与规划会话的判断一致，已逐条核对代码）：

1. **`DeclareSceneEnd` 不幂等**：只拒绝"战斗进行中"，不检查是否已 `Paused` → 同一轮里能建议 4 次，
   每次都 `PauseAsync()` + 推 `host.decision` + 入队一条 `end`；
2. **`StepLoop` 只看 `cancellationToken`**：pause 之后模型仍可继续调工具（实测后面又调了 4 次）；
3. **`RunActorTurnAsync` 开头 `await WaitWhileBlockedAsync(...)`**：pause 之后下一处等待直接卡死，
   直到 120 秒超时或客户端断开。

合起来：**说书人自己把会话暂停了，这一轮后面的步骤在等这个暂停恢复。**

### 13.2 A：幂等

`DeclareSceneEnd` 在战斗检查之后加一道：

```csharp
if (Status == MeetingStatus.Paused)
{
    return new NarratorActionOutcome(false,
        "已处于暂停状态（刚才已经建议过收束），无需再次建议；等导演决定下一步。");
}
```

**不 pause、不推 `host.decision`、不入队**——回执明确告诉模型"已经建议过了"。

### 13.3 B：本轮内主动暂停后立即收尾

新增一个**只表示"说书人自己停的"**的标记 `_pausedByNarratorThisTurn`（每轮 `SayAsync` 开头清零）：

| 场景 | 标记 | `WaitWhileBlockedAsync` | 本轮后续 |
| --- | --- | --- | --- |
| 说书人 `declare_scene_end`（本轮内自己停） | `true` | **不进**（直接返回） | 角色回合、复盘、交互收口全部跳过 |
| 导演点「暂停」（外部暂停） | `false` | 照旧等待 | 照旧（入口处仍会自动恢复，§12 之前那批的语义） |

三处改动：

1. `DeclareSceneEnd` 成功时置位；
2. `RunActorTurnAsync` **在 `WaitWhileBlockedAsync` 之前**检查标记并直接 `return null`
   —— 顺序很关键，那一行就是 219 秒的来源；
3. `SayAsync` 里把"复盘 + 交互收口"包进 `if (!_pausedByNarratorThisTurn)`：
   本轮到此为止，但**已有的角色发言照常落盘**（`_timeline.Append` 在 try 之外，不受影响）。

为什么不去改 `StepLoop` 感知会话状态：那会把 Agent 内核和会话状态机耦合起来，
而 pause 之后"模型还能调工具"本身不是错误——**幂等 + 本轮收尾**已经让重复调用无害。

### 13.4 C：`probe-broken.sheet.json` 挪出扫描目录

它是 `--probe-sheets` 的坏表 fixture，但 `RoleSheetLoader` 用 `SearchOption.TopDirectoryOnly` 扫
`data/roles/*.sheet.json`，于是**每场会话**都会在 `story.jsonl` 写一条 `sheet-invalid` 警告
（用户那场的第一条 warning 就是它）。

已移到 `data/roles/_probe/probe-broken.sheet.json`（子目录不被扫）。要验坏表就把目录参数指到 `_probe`：

```

```

文件不在 git 里（它是开发期 `bin/data/roles/` 下的运行时 fixture），所以这次是**移动文件**、没有代码改动。

### 13.6 边界

- **`StepLoop` 仍然不感知会话状态**：pause 后模型还能在同一 turn 里继续调工具（真机 3 次 declare 就是证据）。
  这是有意的——内核不该耦合会话状态机，重复调用由幂等兜住。代价是"多几次无效往返"，
  可以用模型自己的回执纠正。
- **外部暂停**（导演点暂停）的语义没变：本轮内不会因为标记而跳过；入口处仍会自动恢复（上一批）。
  若希望"外部暂停时回合内也立刻停"，那是另一个改动（需要在每个角色回合前也看 `Status`），本批没做。
- `--probe-sheets` 的坏表样本换了位置，**旧的调用方式（`data/roles`）验不到坏表了**——这是刻意的，
  坏 fixture 不该长在会被会话扫描的目录里。
